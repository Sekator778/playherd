# engine — доменная логика «Толпы против рынка»

Java-модуль (`the project plan` §5): чистая доменная логика раундов «вверх/вниз» (`the project plan` §2; BTC —
рынок по умолчанию, другие пары — `MarketSpec`, см. «Markets») — математика плеча/ликвидации,
симулятор позиции на исторических свечах, и (день 2) полный раундовый движок — кошелёк PLAY,
раунды/ставки, «счёт толпы», сезоны и рейтинги. Без фреймворка, без блокчейна, без
runtime-зависимостей; сервис на Quarkus (D-20) обернёт этот модуль позже.

**Спецификации (авторитетные источники)**:
[`docs/research/hl_liquidation_math.md`](../docs/research/hl_liquidation_math.md) — математика
плеча/ликвидации (`crowdvsmarket.engine.margin`, `round.PositionSimulator`); каждая формула там
помечена javadoc-ссылкой на конкретный подраздел. [`the decision log`](../the decision log)
(D-1…D-21) — продуктовые решения, которые реализует всё остальное (кошелёк, раунды/ставки, счёт
толпы, сезоны, рейтинги); разбор модели, машины состояний и предложений —
[`docs/research/round_engine_design.md`](../docs/research/round_engine_design.md).

## Сборка и тесты

Проект требует Java 21 (глобальный SDKMAN-дефолт остаётся Java 8, не менять — см.
`the maintainer notes`). В каждой команде:

```bash
export JAVA_HOME=$HOME/.sdkman/candidates/java/21.0.11-oracle
export PATH=$JAVA_HOME/bin:$PATH
cd engine
mvn -B verify
```

(`.sdkmanrc` в этой директории задаёт `java=21.0.11-oracle` для тех, кто использует `sdk env`.)

`mvn -B verify` компилирует (`-Xlint:all` с предупреждениями как ошибками), запускает весь
JUnit 5-сьют и собирает `engine.jar`. CI: `.github/workflows/engine.yml`
(actions/checkout, actions/setup-java Temurin 21 с maven-кэшем, `mvn -B verify` в `engine/`) — пока
не может запуститься, у репозитория ещё нет GitHub-remote (день 1, 2026-09-25).

## Что смоделировано

Только **isolated margin, tier0** (notional < 150M USDC) — целочисленное плечо 2..40. Это
осознанный скоуп MVP (спецификация §2.1): tier1 недостижим ни в одном демо-сценарии. BTC — рынок по
умолчанию (кап плеча 40, ставка поддерживающей маржи 0,0125); у любого другого рынка свои кап плеча и
ставка, остальное то же — см. «Markets».

- `crowdvsmarket.engine.margin` — сама математика:
  - `Side` — long/short (`+1`/`-1`, как в формуле Hyperliquid).
  - `MarginTier`/`MarginTable` — тиры маржи BTC (оба тира из спецификации §1.4, включая
    недостижимый tier1 — для полноты данных и для проверки «плечо выше тир-максимума отклонено»),
    построены по рекурсивной формуле `maintenance_deduction` дословно из доков Hyperliquid.
  - `Leverage` — валидированное целое плечо: базовая проверка 2..40, и tier-aware
    `Leverage.forNotional(...)` — дополнительно проверяет капу тира по notional позиции.
  - `LiquidationCalculator` — initial margin, maintenance margin, liquidation price,
    unrealized PnL, payout при закрытии/ликвидации, margin ratio. Все формулы — прямой перевод
    спецификации §2.2 в `BigDecimal` (scale/rounding — §2.6: цены/маржа scale 2 `HALF_UP`, размер
    BTC scale 5, внутренние деления — `MathContext.DECIMAL128`, `isolated_margin` округляется до
    вычисления `liquidation_price`). Три формулы, где участвует ставка поддерживающей маржи `l`
    (`maintenanceMarginRequired`, `liquidationPrice`, `marginRatio`), имеют перегрузку с явной
    ставкой для других рынков; сигнатуры без неё берут BTC-ставку.
- `crowdvsmarket.engine.market` — `Candle`/`Interval`/`CandleSeries`: загрузка CSV-фикстур
  (`src/test/resources/fixtures/`, см. там `PROVENANCE.md`) без внешних библиотек.
- `crowdvsmarket.engine.round` — `Round`/`Position` (форматы данных из `the project plan` §3) и
  `PositionSimulator`: реплей позиции по пути свечей раунда, правила ликвидации по OHLC и
  same-candle/gap-through правила — точно по спецификации §2.3.

**Не смоделировано (осознанно, по спецификации)**: cross margin, tier1, комиссии/funding (оба = 0,
§2.5). Backstop-ликвидация Hyperliquid (полная потеря при equity < 2/3 maintenance margin,
спецификация §1.7) отдельно не моделируется — но при ликвидации в этом движке игрок и так теряет
всю ставку (`payout_on_liquidation = 0`, §2.2) по продуктовому решению **D-7**
(`the decision log`, D-7), а не только в backstop-случае, как на самой Hyperliquid; цена
ликвидации (`liquidation_price`) при этом остаётся точной формулой Hyperliquid, без изменений.

## Раундовый движок (кошелёк, раунды/ставки, счёт толпы, сезоны, рейтинги)

Реализует `the decision log` D-2/D-3/D-5…D-9/D-12…D-19 поверх математики выше. Полный
разбор модели и машины состояний раунда — `docs/research/round_engine_design.md`; здесь только
карта пакетов.

- `crowdvsmarket.engine.ledger` — `PlayAmount` (целые «mojo» PLAY, 1 PLAY = 1000 mojo), `LedgerBook`
  (баланс, лениво выдаваемый стартовый пакет на сезон — D-2/D-12/D-16, ставки, расчёт раунда,
  вывод/ввод PLAY как заявки `requested → confirmed/failed` за интерфейсом `OnChainWalletPort` —
  D-6, ончейн-сторона вне скоупа этого модуля) и append-only лог `LedgerEntry` (на нём проверяется
  консервация PLAY). Две границы сезона: `seasonEndBalance(игрок, сезон)` — баланс на конец сезона
  (`baselineBalance` следующей записи игрока, иначе текущий баланс), из него считается архив
  «богачей» прошлого сезона; `settleRound` пишет счётчики раунда в сезон `Season.of(now)`, если у
  игрока есть запись за него (поздний расчёт раунда, закончившегося в последний день месяца, не
  уходит в новый месяц), иначе в текущий. Движение, датированное прошлым сезоном, но проведённое уже
  после перехода игрока в следующий (выплата такого позднего расчёта, операторская коррекция
  `reverseWithdrawalEffect`/`reverseDepositEffect` заявки прошлого сезона), прибавляется к
  `baselineBalance` каждой более поздней записи: баланс на конец прошлого сезона его включает, рост
  ни одного более позднего сезона — нет, и записи те же, придёт оно до перехода или после. Если у
  игрока нет записи за датирующий сезон, всё остаётся в текущем, как раньше; журнал `entries()` не
  затрагивается.
- `crowdvsmarket.engine.season` — `Season`: календарный месяц UTC (D-10/D-16, предложение).
- `crowdvsmarket.engine.round` (дополнения к существующим `Round`/`Position`/`PositionSimulator`) —
  `RoundWindow`/`RoundClock` (границы раунда по UTC, D-19; окно принадлежит рынку), `PositionSizing`
  (ставка PLAY → размер позиции так, что ставка == initial margin точно — см. design doc «Units»),
  `RoundPrices`/`CandleSeriesRoundPrices` (цены/путь свечей раунда из фикстуры), `Bet`/`BetBook`
  (одна ставка на игрока на раунд, замена/отмена до старта — D-13). `Position.openFromMargin(...)` —
  фабрика поверх `Position.open(...)`; у обеих есть вариант с `MarketSpec` (ставка `l` из рынка),
  а без него позиция BTC.
- `crowdvsmarket.engine.crowd` — `CrowdAccount`: «счёт толпы» (D-5/D-14/D-17) — paper-капитал
  $100 000, раунд входит по стороне большинства по сумме ставок, плечо — средневзвешенное по
  ставкам большинства (HALF_UP, клип 2..кап рынка — 40 для BTC), маржа = 10% текущего капитала.
  Один счёт на рынок (`CrowdAccount(…, MarketSpec)`; конструкторы без рынка — BTC).
- `crowdvsmarket.engine.rating` — `RatingBook`: рейтинги сезона «богачи»/«пророки» (D-9/D-18) с
  порогом N сыгранных раундов (предложение, по умолчанию 10). «Богачи» прошлого сезона считаются от
  баланса на конец того сезона (`LedgerBook.seasonEndBalance`), а не от текущего.
- `crowdvsmarket.engine.player` — `PlayerIdentity`: ник + сокращённый адрес кошелька, только
  модель отображения (D-15).
- `crowdvsmarket.engine.game` — `GameEngine`: оркестратор одной серии раундов (HOURLY или DAILY) —
  ставки → `runRound(window, prices)` открывает позиции по цене открытия, реплеит ликвидацию по
  пути цен, рассчитывает игроков и счёт толпы за один вызов (весь путь цен раунда известен заранее
  и для реплея фикстур, и для будущего живого оракула). Рынок движка — рынок его `CrowdAccount`;
  несколько движков (по одному на рынок и серию) делят один `LedgerBook`.

## Markets (рынки)

D-69 (панели категорий → пары → ставка с плечом внутри пары) делает рынком то, что у движка было
константами BTC: кап плеча и ставку поддерживающей маржи `l`; рынок входит и в id раунда.
Использование: на каждый рынок один `CrowdAccount` и по `GameEngine` на серию (HOURLY, DAILY), все на
одном `LedgerBook` — один баланс PLAY стоит за ставками на любой паре, раунды всех рынков идут в один
`SeasonRecord` игрока.

- `crowdvsmarket.engine.market.MarketSpec(id, maxLeverage, maintenanceMarginRate)`: `id` —
  `[A-Za-z0-9_]{1,32}` (входит в id раунда, поэтому без `-`), `maxLeverage` — 2..40, `l` — правило
  tier 0 Hyperliquid `1/(2*maxLeverage)` (`docs/research/hl_liquidation_math.md` §1.4), которое
  `MarketSpec.of(id, maxLeverage)` считает ровно как `MarginTable.build`. `MarketSpec.BTC` (40, 0,0125)
  несёт тот же `l`, что `MarginTable.BTC.tier(0)` и `LiquidationCalculator.MAINTENANCE_MARGIN_RATE`.
  Прямой конструктор требует ещё `0 < l < 0,5` и `l < 1/maxLeverage` (иначе цена ликвидации лонга выше
  входа, а шорта ниже, и рынок ликвидировал бы каждую позицию на первой свече; `of` это выполняет
  всегда); всё невалидное, `null` вместо `id` или ставки в том числе, — `IllegalArgumentException`.
  `spec.leverage(n)` — плечо с проверкой капа, `spec.clampLeverage(n)` — прижать к `[2, кап]`.
- Формулы и округление те же, ставка — параметр: перегрузки `LiquidationCalculator` с явной ставкой,
  `Position.open`/`openFromMargin(…, spec)`, `ExecutionAdapter.openPosition(spec, …)`. Всё без `spec` —
  BTC, и результаты для BTC побитово прежние (все golden vectors BTC без изменений). У
  `ExecutionAdapter` метод с рынком абстрактный (адаптер, написанный под старый интерфейс, надо
  дополнить), а шестиаргументная форма — удобство для вызывающих: движок зовёт только метод с рынком,
  и её переопределение со своей логикой `CrowdAccount`/`GameEngine` не вызывают.
- `GameEngine.placeBet` отклоняет ставку выше капа рынка и окно чужого рынка (до возврата и резерва:
  отклонённая ставка ничего не меняет), `runRound` — окно чужого рынка; `CrowdAccount` зажимает плечо
  капом рынка (рынок 25x не откроет позицию толпы 40x). `Position.open` кап не проверяет — принятую
  ставку должно быть всегда можно открыть заново при расчёте и реплее.
- Id раунда: BTC — прежний `"<код>-<start>"` (на нём держатся история, ключи БД и хэши результатов),
  остальные — `"<market>-<код>-<start>"`; `RoundWindow.parseRoundId(id)` → `RoundRef(market, interval,
  startMs)` принимает всё, что выдаёт `roundId()`, плюс явную запись BTC `"BTC-<код>-<start>"` как
  псевдоним двухчастной (так id, собранный как рынок + код + старт, разбирается для любого рынка;
  ключом брать `ref.roundId()` — это всегда форма `roundId()`). Старт записан так, как его печатает
  `roundId()` (цифры ASCII, без знака и ведущих нулей); всё остальное — `IllegalArgumentException("malformed
  roundId: …")`. Трёхаргументный `RoundWindow` и перегрузки `RoundClock` без рынка — окна BTC (любое место,
  где окно пересобирается, должно нести `window.market()`, иначе рынок молча станет BTC);
  `RoundClock.next` сохраняет рынок.
- Масштаб цены («lot price»): цена движка — любое число со scale 2, которое передал вызывающий; сервер
  сам масштабирует сырую цену (`× 10^k`), прежде чем отдать её движку. Поэтому `Candle`,
  `PositionSizing` и формулы ликвидации (§2.6) для любой пары те же, что для BTC, а `size` — «лот» рынка.

## Тесты

- `LiquidationCalculatorGoldenVectorTest` — все 20 golden vectors спецификации (§3): initial
  margin/liquidation price/maintenance margin, плюс `payout_on_liquidation` (0 по D-7) и, на
  заявленной в спецификации `close_price` для каждой группы, `unrealized_pnl`/
  `payout_at_round_close`.
- `LiquidationCalculatorInvariantTest` — структурные инварианты: `long liqPx < entry < short
  liqPx`; liqPx монотонно движется к entry с ростом плеча; equity на liqPx равна динамической
  maintenance margin *на этой же цене* (не путать с entry-based `maintenance_margin_required`,
  который использует `marginRatio`, — см. javadoc теста); невалидное плечо (1, 41, выше
  тир-максимума) отклоняется.
- `HistoricalScenarioTest` — все 25 сценариев спецификации (§5: 10 крупнейших дневных падений, 10
  ростов, 5 экстремальных часовых свечей) воспроизводят ровно те же множества ликвидированных
  плеч, плюс сверка, что фикстура реально содержит те же OHLC, что процитированы в спецификации.
- `FullSweepReplayTest` — по каждой свече обеих фикстур (`hl_btc_1d.csv`, `hl_btc_1h.csv`) и
  каждому плечу 2..40, обе стороны: `PositionSimulator` сверяется со второй транскрипцией той же
  математики, написанной отдельно внутри теста (не вызывающей `LiquidationCalculator`) — не
  независимая проверка формул (обе — транскрипции одной и той же спецификации, см. javadoc
  класса), но ловит Java-уровневые ошибки переноса (опечатка, знак, off-by-one) в одной из двух
  реализаций, которые не поймали бы одни golden vectors.
- `CandleSeriesTest` — фикстуры грузятся с задокументированным числом строк/первой-последней
  свечой (см. `PROVENANCE.md`), OHLC-инварианты (`low <= open/close <= high`) по всем реальным
  свечам обеих фикстур.
- `CandleTest` — сам компактный конструктор `Candle` отклоняет невалидные OHLC (`high < low`,
  `open`/`close` вне `[low, high]`, неположительная `low`).
- `PositionSimulatorMultiCandleTest` — многосвечные пути (в отличие от всех остальных тестов,
  использующих один-единственный свечной путь): дневной раунд, реплеенный по его 24 часовым
  свечам из `hl_btc_1h.csv` (реальные последовательные данные), плюс синтетические многосвечные
  пути — ликвидация обнаруживается на свече в середине пути с правильным временем свечи,
  закрытие раунда (`Settled`) при отсутствии ликвидации на всём пути, приоритет ликвидации над
  закрытием раунда, если и то и другое происходит в последней свече пути.
- `PlayAmountTest`/`SeasonTest`/`PlayerIdentityTest` — value-типы кошелька/сезона/отображения
  (округление до mojo, UTC-границы месяца/года, формат «ник (сокращённый адрес)»).
- `RoundClockTest` — границы часового/дневного раунда по UTC, `next()` даёт смежное окно той же
  длины (машина «всегда один идущий + один открытый для ставок раунд», D-19).
- `PositionSizingPropertyTest` — property-тест на ~6250 (цена × сэмпл) комбинаций: `round2(size *
  price / leverage) == margin` для реальных цен из обеих фикстур плюс синтетических крайних цен —
  доказательство того, что ставка PLAY есть initial margin позиции точно (design doc «Units»).
- `BetBookTest` — одна ставка на игрока на раунд (повторная `place` замещает и возвращает
  предыдущую), независимость раундов/игроков друг от друга, `cancel`/`clear`.
- `CandleSeriesRoundPricesTest` — часовой раунд на часовой серии даёт путь из одной свечи; дневной
  раунд на часовой серии даёт полный внутридневной путь (те же 24 реальные свечи, что и в
  `PositionSimulatorMultiCandleTest`); окно без свечей — ошибка.
- `LedgerBookTest` — ленивая выдача стартового пакета на первую активность сезона с фиксацией
  baseline (D-16), минимальная ставка и баланс никогда не уходит в минус (D-12), расчёт раунда
  (payout/пороги «пророков»), полный цикл вывода/ввода PLAY через `requested/confirmed/failed`
  (D-6), и «лог операций воспроизводит баланс» — база инварианта консервации.
- `CrowdAccountTest` — большинство именно по сумме ставок (не по числу игроков), средневзвешенное
  плечо HALF_UP, маржа 10% от **текущего** (не стартового) капитала, ликвидация счёта толпы теряет
  ровно маржу, капитал накапливается между раундами.
- `RatingBookTest` — точная формула «богачей» (D-18) на подставных данных, исключение плоских
  раундов из знаменателя «пророков», исключение ниже порога N раундов, сортировка списков.
- `GameEngineRoundLifecycleTest` — раунд с ликвидацией одного игрока и расчётом другого,
  модификация ставки до старта (рефанд старой ДО резерва новой — иначе увеличение ставки до полного
  баланса ложно отклонялось бы), отмена ставки, счёт толпы торгует по фактическим ставкам раунда,
  несколько DAILY-раундов на часовой фикстуре.
- `MonthLongHourlySimulationTest` — весь апрель 2026 (UTC, 720 часовых раундов) на реальной
  `hl_btc_1h.csv`, 50 детерминированных игроков (always-40x, contrarian, follow-the-crowd, общая
  seeded-случайная стратегия с шансом изменить ставку до старта раунда). Проверяет: одна позиция на
  игрока на раунд, независимая пересборка формулы счёта толпы из фактических исходов раунда (второй
  код, не вызывающий `CrowdAccount`), баланс никогда не отрицательный, два независимых инварианта
  консервации PLAY (лог операций воспроизводит баланс; итоговый баланс = выданные пакеты + сумма
  чистых выигрышей/проигрышей раундов — «дом» чеканит выигрыши и сжигает проигрыши, включая полную
  потерю ставки при ликвидации, D-7 — независимо накопленная во время цикла из отчётов движка, а не
