# Дорога к архитектуре LMAX

Дата: 2026-10-16. Основание — D-95 (`the decision log`): цель — миллионы ставок в секунду при малых ресурсах; брать лучшее существующее (LMAX), не изобретать; сейчас не переписывать, а закладывать фундамент. Что есть сейчас и что мешает — [`architecture_review_2026-10-16.md`](architecture_review_2026-10-16.md).

## 1. Что такое LMAX и что из этого у нас уже есть

Источник — Martin Fowler, «The LMAX Architecture», https://martinfowler.com/articles/lmax.html (прочитано 2026-10-16): розничная торговая система, которая обрабатывает «6 million orders per second on a single JVM thread». Устройство по статье:

| Часть LMAX | Что делает | У нас сейчас |
|---|---|---|
| Business Logic Processor (BLP) | вся логика в памяти, в одном потоке, без блокировок и без ввода-вывода | движок в памяти и чистый (`engine/`), состояние по рынкам разделено (`EngineHub`) — есть; но меняется под общей блокировкой из многих HTTP-потоков, с записью в Postgres внутри (`GameService.java:731-837`) — нет |
| Event sourcing | состояние = результат входных событий; восстановление — повтор | есть: `game_events`, один путь применения событий (`EventApplier`) |
| Input Disruptor | кольцевой буфер перед BLP; параллельно — запись входа в журнал, репликация, разбор | нет: ставка пишется в Postgres синхронно, по одной |
| Снимки | BLP периодически сохраняет снимок; перезапуск = снимок + хвост журнала | нет: перезапуск перечитывает все события (`EventStore.java:57-62`) |
| Output Disruptor | результаты уходят клиентам отдельным потоком | нет: клиенты опрашивают сервер раз в 2 с |

## 3. Шаги

Каждый шаг: проект → ревью архитектора → «ок» Алекса → код → замер. Игра не останавливается ни на одном шаге.

| # | Шаг | Что даёт |
|---|---|---|
| 0 | Модуль `bots` (идёт) | боты по стратегиям; позже — генератор нагрузки для замеров |
| 1 | Фундамент из ревью (§4 там): колонки `market`/`player_id` в `game_events`, интерфейс снимка у движка, запрос к базе вынести из-под блокировки, кэш сессий, `clientRequestId` в ставке, правило «нет базы и сети под блокировкой движка» (ArchUnit), метрики удержания блокировки, свечи RPC | без изменения поведения; каждый пункт — заготовка под шаги 3–5 |
| 2 | Замер: нагрузочный прогон ставок (боты как клиенты), ставок в секунду и задержка p99 | точка отсчёта; без неё дальше не идём |
| 3 | Ядро LMAX: ставки и расчёты становятся командами в Disruptor; один поток-писатель вместо общей блокировки; журнал входа пишется параллельно и пачками; Postgres — асинхронные read-models | главный прирост; число — по замеру |
| 4 | Снимки состояния и быстрый перезапуск; горячий резерв, повторяющий журнал | перезапуск за секунды, отказоустойчивость |
| 5 | Выход: push клиентам (WebSocket) вместо опроса; слой API без состояния на нескольких машинах | нагрузка от клиентов уходит с ядра |
| 6 | Разделение по рынкам (несколько ядер), если одного ядра мало по замеру; балансы — через отдельный счёт/резервирование | масштаб за пределы одной машины |

## 4. Язык ядра — по замеру, не заранее

Алекс, 2026-10-16: «ядро на Java не означает, что мы сейчас не можем развернуть всё на Rust». Ревью архитектора (§6): переписать горячий путь на Rust сейчас ничего не даст, пока блокировка одна и запись в базу синхронная; перенос ядра позже облегчён — ядро чистое, события — JSON с явными полями. Поэтому на шаге 3, где ядро (BLP) пишется заново в любом случае, — два прототипа, Java и Rust, повторяют один и тот же журнал `game_events`: балансы должны совпасть до единицы, сравниваются ставки в секунду на ядро, задержка p99 и память; язык выбирается по числам. Для Rust есть порт Disruptor — `disruptor` 4.4.0, https://github.com/nicholassm/disruptor-rs (crates.io, обновлён 2026-08-08).

## 5. Образец: exchange-core

https://github.com/exchange-core/exchange-core (Java, Apache-2.0, 2 647 звёзд, последний push 2023-10): движок биржи на LMAX Disruptor, Agrona и OpenHFT; README: одна книга заявок — «5M operations per second on 10-years old hardware»; конвейер по ядрам — шарды счетов пользователей отдельно от шардов инструментов. Это ответ на нашу будущую трудность шага 6: лимиты казны общие, поэтому счета и рынки делятся раздельно.

Rust остаётся для блокчейна (ревью §6); язык ядра — по §4.

## 6. Сверка с независимым ревью (2026-10-16)

Второй ревьюер (другая модель; про LMAX, первое ревью и этот план ему не говорили, читать их запретили) — [`architecture_review_independent_2026-10-16.md`](architecture_review_independent_2026-10-16.md).

- **Сошлось.** Сравнив пять семейств (сервис вокруг БД; акторы Pekko/Orleans; Kafka/Flink; ядро с одним писателем и журналом; TigerBeetle для балансов), он сам выбрал ядро с одним писателем и журналом — паттерн LMAX, выращенный из текущего кода. Главный предел — тот же: общая блокировка и синхронный коммит. Язык ядра — Java. Переписывать сейчас — нет.
- **Новое у него.** (1) Проверка лимитов казны перебирает все ставки раунда — O(N²) на раунд (`GameService.java:2286-2296`, проверено). (2) История леджера копится в памяти навсегда (`LedgerBook.java:41`, `:880-888`). (3) Журнал — не единственный источник правды: игроки, рынки, номер оракула пишутся мимо событий. (4) Свои шаги F1–F8 и этапы S1–S9, у каждого — измерение-триггер; Disruptor, Chronicle/Aeron, Raft, push, Rust — только по триггеру.
- **Расходится с §4 этого плана.** Гонку прототипов Java и Rust сейчас он считает бессмысленной: Rust строить, только если Java не уложится в заранее заданный бюджет на бенчмарке повтора журнала (его §3.5, этап S7). Это сильнее нашего §4 — принимаем.
- **Главное.** При правилах D-92 потолок задаёт экономика, а не техника: лимиты казны (0,25 % на сторону рынка, 1 % на крипто-корзину, `EconomyLimits.java:25-27`, проверено) пропускают не больше ≈5,2 млн минимальных ставок за 3-минутный раунд по 18 рынкам (≈29 тыс./с в среднем; арифметика по константам, не замер), при обычных ставках — в ~50 раз меньше. Дальше — только решения экономики (нетто-экспозиция вместо брутто одной стороны, казна пропорционально обороту, тотализатор) — через экспертов по D-91.

Объединённый порядок — на сверку с Алексом.

## 7. Шаг 1: кэш сессий и `clientRequestId` (ветка `feature/arch-sessions-idempotency`)

- **Кэш сессий** (`auth/SessionCache.java`, `SessionService`): только чтение-сквозь таблицы `sessions`, в памяти процесса, ограничен (20 000 записей), TTL 30 с (`herd.session.cache-ttl-seconds`), запись никогда не живёт дольше `expires_at_ms` строки. Кэшируются только найденные сессии (промах всегда идёт в базу). Выход (`signOut`) удаляет строку и запись сразу; чтение, начатое до выхода, не может вернуть запись после него (счётчик поколений). **Правило для нескольких экземпляров сервера (вне рамок сейчас):** запись кэша — копия строки, а не источник правды; на другом экземпляре вышедшая сессия живёт не дольше TTL, поэтому TTL остаётся коротким, а перед включением второго экземпляра нужна общая инвалидация. Ключи ботов в кэше не нуждаются: поиск ключа по хешу — уже память (`PlayerDirectory.byKeyHash`), отзыв действует сразу.
- **`clientRequestId`** (`PlaceBetRequest`, `BetPlaced`, `domain/BetRequests.java`): необязательный id одного нажатия (1–64 символа `A-Za-z0-9-_`). Повтор того же id от того же игрока в течение 10 минут (по времени запроса) не ставит вторую ставку и возвращает первый ответ; тот же id для другой ставки — `400 BAD_REQUEST`; отказанная ставка не запоминается. Память — часть состояния движка: её ведёт `EventApplier` по полю `BetPlaced.clientRequestId` (в событии только если id прислан — байты старых событий не меняются), поэтому пересборка из журнала её восстанавливает; она же в снимке (строки `betRequest`, формат остаётся 1: снимок без этих строк = пустая память = то, что строит повтор журнала без id). Границы: 10 минут и 50 000 записей, старые уходят при добавлении новой (по `atMs` событий, не по часам машины). `cancelBet` и так идемпотентен (нет ставки — ничего не пишется), id не нужен.

## 8. Шаг 3, часть «журнал»: Chronicle Queue (D-107, 2026-10-21)

Журнал событий перенесён из таблицы `game_events` в Chronicle Queue (ветка `feature/journal-chronicle`, не влита): запись пачки писателя — одна запись очереди с `msync` до ответа; Postgres — копия, которую пишет отдельный поток. Устройство, разбор записей транзакции пачки, эксплуатация, замеры и открытые вопросы — [`journal_chronicle_2026-10-21.md`](journal_chronicle_2026-10-21.md); первоисточники по сбросу на диск и флагам Java 21 — `docs/kb/topics/methods.md`, «Хранение журнала». Замер на Linux-томе показал, что запись пачки стоит около 2,2 мс против 2,6 мс коммита Postgres, поэтому выигрыш на скорости зависит от диска сервера (там не измерялось). Разделение по рынкам (шаг 6) и Disruptor (остаток шага 3) этим не затронуты.
