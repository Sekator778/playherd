## Сводка

**Что есть.** Ядро уже устроено как in-memory движок с журналом событий: состояние в памяти (`EngineHub`), единственный путь изменения (`EventApplier`), журнал `game_events` в Postgres, полный реплей при старте, fail-stop, если память могла разойтись с БД. Это та же семья, что LMAX. Но «единственный писатель» реализован глобальным `ReentrantReadWriteLock`, который держится через синхронный `COMMIT` Postgres на **каждую** ставку и через **весь** расчёт раунда.

**Что ограничивает (по коду, не по замерам):**
1. Глобальная блокировка поверх `COMMIT`: ставки идут строго по одной, групповой коммит Postgres сработать не может.
2. Проверка лимитов казны перебирает все ставки раунда: O(N) на ставку, O(N²) на раунд.
3. Расчёт раунда — O(ставок) вместе с записью N строк и JSON под той же блокировкой. Границы раундов всех 18 рынков совпадают.
4. История движений в памяти не ограничена (`LedgerBook.entries`); при старте журнал реплеится с нуля, снапшотов нет.
5. Чтения идут под той же блокировкой, часть из них стоит O(игроков) или O(всех движений). Каждый клиент опрашивает сервер раз в 2–3 с.

**Рекомендация — семейство D: in-memory ядро с одним писателем и журналом (паттерн LMAX), выращенное из текущего кода.** Без Kafka, без кластера акторов, без переноса логики в SQL. Что именно:
- отдельный поток-писатель с очередью команд и групповым коммитом журнала;
- снапшоты с хешем состояния;
- всё, что не нужно для решения «принять / отклонить / рассчитать», — проекции вне ядра.

Горизонтальное масштабирование идёт в таком порядке: сначала чтения (последователи, которые читают журнал); затем конвейер «шарды счетов игроков + один глобальный риск-этап» внутри одной машины (как в exchange-core); затем репликация журнала.

**Язык ядра — Java (21, текущий `engine/`).** Ни одно из ограничений 1–5 не связано с языком. Rust в ядро — только если Java-сборка после устранения пунктов 1–5 не уложится в заранее записанный бюджет на бенчмарке реплея (§3.5). Опцию «всё на Rust» дёшево держать открытой: формат журнала и хеш состояния служат языконезависимым контрактом (F4, F5).

**Первые шаги (дёшево, без переписывания):**
- F1 — харнес измерений;
- F2 — O(1)-агрегаты экспозиции и поиска ставки;
- F3 — история движений уходит из памяти в read-model;
- F4 — журнал самодостаточен, применение события чистое;
- F5 — снапшоты и хеш состояния;
- F6 — поток-писатель с групповым коммитом вместо глобальной блокировки;
- F7 — расчёт раунда: ядро считает, проекции пишут вне блокировки;
- F8 — чтения из опубликованных снимков без блокировки.

**Главное несогласие с очевидным выбором.** При «миллионах» потолок задаёт экономика, а не язык и не инфраструктура. Выпуск — 100 млн PLAY, лимиты казны — 0,25% на сторону рынка и 1% на крипто-корзину. При таких правилах проходит не больше ≈5,2 млн ставок за 3-минутный раунд по 18 рынкам, и то только если каждая ставка минимальна (100 PLAY × x2). В среднем по раунду это ≈29 тыс. ставок/с (арифметика по константам кода, §6.2). Дальше рост числа пользователей растит отказы `EXPOSURE_LIMIT_EXCEEDED`, а не принятые ставки. Гонка прототипов Java против Rust сейчас преждевременна: она меряет то, что не ограничивает систему.

Итого на одну ставку: один `SELECT` и одна транзакция с `COMMIT` внутри глобального эксклюзивного участка. В `docker-compose.yml:51` у Postgres переопределён только `shared_buffers`, поэтому `synchronous_commit` стоит по умолчанию (значение по умолчанию в этом обзоре по документации не сверялось — UNVERIFIED).

**Вывод (опирается на пункты 3–10):** потолок пропускной способности ставок равен `1 / t_hold`, где `t_hold` — время удержания блокировки (SELECT + INSERT + COMMIT + применение). Число ядер на потолок не влияет. `t_hold` не измерялось. Пример только для понимания формулы, не замер: при `t_hold` = 2 мс потолок — 500 ставок/с.

**Групповой коммит Postgres здесь не поможет.** Документация Postgres: `commit_delay` / группа коммитов «can only help when (1) there are some concurrently committing transactions» (postgresql.org, WAL Configuration, v16). Под глобальной блокировкой у игры в каждый момент коммитит не больше одной транзакции. **Вывод:** механизм, который в Postgres объединяет fsync нескольких транзакций, для ставок не включается никогда.

**Блокировка нечестная.** `new ReentrantReadWriteLock()` создаётся без `fair` (`GameService.java:212–213`). Javadoc Java 21: «A nonfair lock that is continuously contended may indefinitely postpone one or more reader or writer threads». Чтения (опросы клиентов) и записи (ставки, расчёт) конкурируют за один замок.

### 1.2 Расчёт раунда

- **Планировщик — один поток.** Тик раз в секунду, `concurrentExecution = SKIP` (`server/.../scheduler/RoundSchedulerService.java:185`). Внутри последовательно: тик ботов, затем расчёт по каждому рынку × серии, затем публикация оракула (`:240–268`).
- **Фаза 1 без блокировки:** цены окна (`GameService.java:905`).
- **Фаза 2 под write-блокировкой** (`GameService.java:907–943`): проверка в БД (`:909`), затем **одна транзакция** (`:924–930`):
  - запись события и применение. `GameEngine.runRound` (`GameEngine.java:187–237`) для каждой ставки открывает позицию, прогоняет её по пути цены (`PositionSimulator`), применяет потолок выплаты и проводит расчёт в леджере;
  - `storeSettledResult` (`GameService.java:974–1033`): копия идентичностей всех игроков (`:977` → `PlayerDirectory.java:171–177`); по каждой ставке DTO, запись для хеша и строка истории; канонический JSON и sha256 (`:1025–1026`); строка `round_results` с `positions_json` **всех** позиций и строки `player_round_history` (`:1029–1031`); запись оракула с резервированием `seq` (`:1059–1065`).
- **Результат зависит от порядка ставок.** Потолок выплаты = `min(20 × stake, 0,1% казны)`; казна читается внутри цикла по ставкам (`GameEngine.java:219–223` → `LedgerBook.payoutCapTreasury` `:832–834`) и сдвигается после расчёта каждой ставки (`LedgerBook.java:330–332`). **Вывод:** без изменения правила расчёт нельзя распараллелить по игрокам.
- **Границы синхронны.** «Every market runs on the same clock (a window belongs to a market, the boundaries do not)»; на стенде границы :00/:03/… и :00/:15/… (`server/.../domain/RoundCalendar.java:15–16`, `:21`). Значит все 18 рынков закрывают 3-минутный раунд в одну секунду, а на 15-минутной границе закрываются обе серии. Ставка идёт на следующий раунд (`README.md:36`, D-19). **Вывод:** у границы стоят рядом два пика — последние секунды приёма ставок на раунд N+1 и расчёт раунда N. Пока идёт расчёт, ставки и чтения ждут блокировку.

### 1.3 Балансы и чтения

- Один `LedgerBook` на все рынки: один баланс PLAY стоит за ставками на любом рынке (`server/.../domain/EngineHub.java:15–18`, `:75–79`). Сам он не потокобезопасен, его защищает блокировка `GameService` (`EngineHub.java:30–33`).
- Каждое изменение баланса заменяет неизменяемый `PlayerAccount` и **навсегда** добавляет `LedgerEntry` в список в памяти (`LedgerBook.java:880–888`, список — `:41`). Карта сезонов игрока копируется при каждом обновлении (`:895–900`, `:542–544`).
- Деньги в леджере — `long` mojo (`PlayAmount.java:22`). Позиции и выплаты считаются в `BigDecimal` с явными масштабами и округлением (`GameEngine.java:192–223`; `RoundingMode.DOWN` — `:221`).
- Чтения идут под read-блокировкой. Дорогие среди них:
  - `myLedger` копирует всю историю движений всех игроков (`GameService.java:1574` → `LedgerBook.entries()` `:123–125`, `List.copyOf`);
  - `ratings` перебирает и сортирует всех игроков на каждый запрос (`GameService.java:2064–2087`, `RatingBook.java:58`, `:85`);
  - `playersTotal()` — O(игроков) (`LedgerBook.java:741–747`).
- Клиенты опрашивают `markets`, `priceSeries`, `myPositions`, `crowdOverview` раз в 2–3 с (`RpcResource.java:56`). Ответ `markets` кэшируется примерно на 1 с (`MarketViewService.java:57`).
- Вход игрока тоже идёт под write-блокировкой (`GameService.java:385–428`): запрос в БД по лимиту регистраций (`:398`), резервирование индекса (`:406`), **две отдельные транзакции** — строка `players` (`:408–409`) и событие (`:414`).

### 1.4 Рестарт и восстановление

- `EventStore.loadAll` читает весь журнал в один `List` (`EventStore.java:58–63`). Новый хаб строится в стороне, состояние подменяется одним шагом (`scheduler/EngineRebuildService.java:170–200`). Снапшотов нет — это осознанный выбор «(а) переигрывать поток команд» (`docs/research/server_design.md` §3).
- **Измерено** (единственный замер производительности ядра в репозитории): пересборка стоит 25 мс + 5,6 мкс на событие журнала, 510 мс при 91 тыс. событий (`docs/research/markets_architecture.md:180`, ревью ядра 2026-10-02, находка 3).
- Пока идёт пересборка, всё, что читает память, отвечает 503 (fail-stop, `EngineRebuildService.java:32–48`).
- **Вывод (линейная экстраполяция замера выше, не замер):** при 10⁹ событий пересборка займёт ≈5 600 с, около 1,5 часа простоя. Список всех событий из `loadAll` к тому же должен целиком поместиться в куче.

## 2. Семейства архитектур для этой нагрузки

### 2.0 Что требует нагрузка (из кода)

| # | Требование | Где |
|---|---|---|
| R1 | Один баланс игрока на все рынки | `EngineHub.java:15–18` |
| R2 | Казна — контрагент каждой ставки. Двигается при каждом расчёте, при каждом стартовом пакете, при части возвратов комиссий, при уходе ботов и при сборе комиссий | `LedgerBook.java:330–332`, `:198–200`, `:285–290`, `:712–715`, `:699` |
| R3 | Лимит экспозиции на (рынок, серия, раунд, сторона) и общая крипто-корзина по 6 рынкам | `EconomyLimits.java:25–27`; `GameService.java:2255–2271` |
| R4 | Предохранитель: казна против своего 30-дневного максимума | `LedgerBook.java:849–856` |
| R5 | Потолок выплаты от текущей казны, зависит от порядка расчёта | §1.2 |
| R6 | Одна ставка игрока на раунд серии рынка | `BetBook.java:9–12` |

**Вывод (на R2–R5):** казна, экспозиция и предохранитель — глобальные «горячие» величины. Их трогает почти каждая ставка или каждый расчёт. Это главный фактор выбора: архитектура, которая раскладывает состояние по узлам, должна либо собрать эти величины в одном месте, либо ослабить правила, а это уже экономическое решение. TigerBeetle описывает ту же проблему: «a small number of hot accounts are often involved in a large proportion of the transactions, so the shards responsible for those accounts become bottlenecks» (docs.tigerbeetle.com, Performance).

### 2.1 A. Сервис вокруг БД, горизонтально масштабируемый

Stateless-узлы приложения; источник правды — Postgres; балансы и счётчики меняются атомарными `UPDATE … WHERE balance >= x` или под `SELECT … FOR UPDATE`.

- **Соответствие нагрузке.** Балансы игроков — хорошо: строка на игрока. Казна и счётчики экспозиции — горячие строки: каждая ставка обновляет строку своей стороны раунда и строку крипто-корзины, каждый расчёт — казну. На блокировке горячей строки ставки сериализуются так же, как сегодня, только теперь внутри критического участка ещё и сетевые круги. TigerBeetle о том же: «locks over the network are very expensive!». Смягчения — одно обновление казны за раунд, счётчики экспозиции, разрезанные на части с нестрогими лимитами. Оба меняют правила.
- **Ресурсы.** Каждая ставка — транзакция с WAL; групповой коммит работает для параллельных транзакций (документация Postgres), то есть лучше, чем сегодня. **Вывод:** CPU и ввод-вывод на ставку выше, чем при ядре в памяти, потому что каждое решение проходит через СУБД.
- **Задержка:** миллисекунды на ставку (для этой системы не измерено — UNVERIFIED).
- **Отказы и восстановление:** классические (реплика Postgres и переключение). Самая простая модель в голове.
- **Эксплуатация силами одного человека:** просто, пока один primary. Шардирование записей — Citus (AGPL-3.0 по GitHub API) или распределённый SQL (CockroachDB, YugabyteDB: лицензия по GitHub API `NOASSERTION`, условия не читались — UNVERIFIED) — уже сложно.
- **Прецеденты:** источника с числами для такой нагрузки в этом обзоре не найдено (UNVERIFIED).
- **Цена для Herd.** Семантику `LedgerBook` и `GameEngine` придётся переносить в SQL или поднимать состояние из БД под каждую команду. 7 321 тест движка (`README.md:40`) проверяет объекты в памяти — их придётся перенацелить. Теряется детерминированный реплей, на котором стоят аудит и оракул (вывод).

### 2.2 B. Акторы и шардирование сущностей (Apache Pekko Cluster Sharding, Microsoft Orleans)

- **Соответствие.** Игрок как сущность — естественно; раунд рынка со ставками и экспозицией — естественно. Казна — одна сущность: каждый расчёт и каждая проверка экспозиции идут сообщением к одному актору, это последовательная горячая точка. Связка «зарезервировать баланс у актора игрока + проверить экспозицию у актора рынка + казна» требует саги с компенсацией (вывод).
- **Документация Pekko:** «Pekko Persistence is based on the single-writer principle, for a particular PersistenceId only one persistent actor instance should be active». Предупреждение: стратегия downing, которая может расколоть кластер, приведёт к тому, что «multiple shards and entities being started, one in each separate cluster!».
- **Лицензии.** Akka с версии 2.7 (октябрь 2022) — Business Source License 1.1; организациям с выручкой до $25 млн платить не нужно, но коммерческая лицензия всё равно обязательна (блог akka.io, 2022-09-07). Apache Pekko — Apache-2.0 (GitHub API). Orleans — MIT (GitHub API), но это .NET, то есть смена языка.
- **Прецеденты:** Microsoft использует Orleans в Azure, Xbox, Skype, Halo, PlayFab, Gears of War (Microsoft Learn, Orleans overview).
- **Ресурсы и задержка:** состояние сущности в памяти — хорошая локальность. Сверху — накладные расходы кластера (членство, координатор шардов, сериализация между узлами); межсущностные транзакции добавляют сетевые прыжки (вывод).
- **Отказы:** перебалансировка, плагин хранения, стратегия downing.
- **Эксплуатация одним человеком:** сложно.
- **Цена:** движок придётся перестроить в протоколы сообщений.

### 2.3 C. Партиционированный лог + потоковые обработчики (Kafka / Redpanda + Kafka Streams / Flink)

- **Соответствие.** «Kafka only provides a total order over messages within a partition, not between different partitions in a topic» (kafka.apache.org, документация 0.9.0, Introduction). Партиции по игроку дают локальную проверку баланса, но экспозицию и казну нужно вести отдельным этапом в одной партиции. Получается двухэтапный конвейер с транзакциями между топиками, и глобальный этап снова однопоточный (вывод). Партиции по рынку не подходят: баланс игрока охватывает все партиции.
- **Прецедент:** 2 024 032 записи/с на трёх брокерах, записи по 100 байт; сквозная задержка — медиана 2 мс, p99 3 мс, p99,9 14 мс (Jay Kreps, LinkedIn Engineering, 2014-04-27).
- **Ресурсы.** Для надёжности нужны как минимум три брокера (бенчмарк с репликацией ×3), плюс приложение-обработчик со своим хранилищем состояния. **Вывод:** для VPS на 4 vCPU и 7,9 ГБ это тяжело.
- **Задержка:** миллисекунды (по бенчмарку) — для 3-минутных раундов достаточно.
- **Отказы:** сильная сторона — реплицированный лог и реплей. Exactly-once требует аккуратной настройки.
- **Эксплуатация одним человеком:** сложно.
- **Лицензии:** Kafka и Flink — Apache-2.0 (GitHub API); Redpanda — по API лицензия не определена (UNVERIFIED).
- **Место в Herd:** позже, как транспорт журнала к read-моделям и аналитике. Не как ядро.

### 2.4 D. In-memory ядро с одним писателем, событийный журнал (паттерн LMAX)

- **Соответствие.** R1–R5 обрабатываются в одном потоке, без распределённой координации. После F2 работа на ставку — O(1). Расчёт раунда — цикл в памяти. Детерминизм даёт реплей, аудит и последователей (R8).
- **Прецеденты с числами:**
  - **LMAX:** «6 million orders per second on a single thread», Java; входные события журналируются и реплицируются до обработки; снапшоты по ночам; рестарт — «less than a minute» (Martin Fowler, 2011-07-12).
  - **exchange-core:** «5M operations per second» на Xeon X5690; при 1M оп/с 99,9% — 22 мкс. Конвейер: «each CPU core is responsible for certain processing stage, user accounts shard, or symbol order books shard»; журнал и снапшоты. Apache-2.0. Последний push — 2023-10-08 (GitHub API): как образец для чтения годится, как зависимость — нет.
  - **Coinbase Exchange:** «implemented in both Golang & Java, with E2E latency as low as sub-50 microseconds», Raft (USENIX SREcon23, 2023-03-22). Урок отказа: Raft-кластер стоял в одной placement group одной зоны AWS; потеря 3 из 5 узлов лишила его кворума, восстановление заняло «much of the following day» (InfoQ, 2026-06-16).
  - **Hyperliquid (Rust):** «approximately 200k orders/sec», «The current bottleneck is execution» (документация HyperCore).
  - **TigerBeetle:** «uses a single core by design», пакеты до 8 190 переводов.
- **Ресурсы:** бизнес-логике достаточно одного ядра CPU. После F3/F5 память пропорциональна живому состоянию, а не всей истории.
- **Задержка:** определяется интервалом пакета журнала (настраивается). **Вывод:** для 3- и 15-минутных раундов десятки миллисекунд приемлемы.
- **Отказы:** журнал + снапшот + реплей; fail-stop уже есть (`EngineRebuildService`). Высокая доступность — горячий резерв, который реплеит журнал; позже Raft (Aeron Cluster: «an implementation of Raft Consensus», реплицируемый лог, снапшоты, реплей; Apache-2.0).
- **Эксплуатация одним человеком:** просто на этапе D1 (один процесс + Postgres, как сейчас); средне с горячим резервом; сложно с Raft.
- **Ограничения:** масштаб вертикальный — один поток. Нужна дисциплина: в применении события нет ввода-вывода, часов и внешних запросов. Сегодня это нарушено: `EventApplier.java:203–206` читает `PlayerDirectory`, расчёт делает работу с БД и JSON под блокировкой.
- **Цена для Herd:** эволюция, а не переписывание. Журнал, единственный путь применения, fail-stop и входные данные в событиях (цены и путь в `RoundResolved` — `EventApplier.java:98–107`; время прихода в `BetPlaced`) уже есть.

### 2.5 E. Отдельная леджер-СУБД (TigerBeetle) как компонент балансов

- **Что это:** double-entry леджер; «single leader node», один поток; пакеты до 8 190 переводов. Флаги счёта `debits_must_not_exceed_credits`, связанные события (`linked`), двухфазные переводы (pending → post/void). Официальные клиенты есть для Java и Rust (docs.tigerbeetle.com). Apache-2.0.
- **Соответствие (вывод):** балансы и казна — счета; резерв ставки — pending-перевод; расчёт — post или void. Ложится хорошо. Не покрывает: счётчики экспозиции, сезоны и пакеты, потолки выплат, счёт толпы — они остаются в ядре. Появляются два источника правды и задача их согласования.
- **Когда:** когда понадобится независимый реплицированный и проверяемый леджер (например, если продукт уйдёт от игрушечных денег). Сейчас не нужен.

### 2.7 Выбор: D, выращенный из текущего кода

1. Глобальные величины R2–R5 — сердце экономики D-92. Один писатель держит их без распределённых протоколов; A, B и C всё равно сводят их к одной последовательной точке, только дороже.
2. Опубликованные одиночные потоки такого ядра обрабатывают миллионы операций в секунду (LMAX, exchange-core). Это выше экономического потолка Herd (§6.2), так что вертикального масштаба хватает с запасом (вывод из сопоставления этих двух чисел).
3. Ресурсы минимальны: одно ядро CPU, память по живому состоянию, журнал пакетами. Это прямо цель владельца «очень мало ресурсов».
4. Около 80% уже есть в коде (§2.4). Переход — шаги F1–F8, а не переписывание.
5. Детерминизм, который нужен оракулу и аудиту (R8), в D — свойство архитектуры, а не дисциплина отдельных разработчиков.

Горизонтальный масштаб в D там, где он реально нужен: чтения — последователи, которые читают журнал (S1); после этого — конвейер «шарды счетов + глобальный риск» внутри одной машины (S4).

### 2.8 Что изменило бы моё мнение

- **Экономика уйдёт от общей казны-контрагента** (например, пулы по рынку и раунду, где игроки — контрагенты друг друга, и баланс по рынкам). Тогда естественным станет разбиение по рынкам, и C или «писатель на рынок» станут выгоднее.
- **Понадобится запись active-active в нескольких регионах при общей казне.** Это не решается ни одной из архитектур без разделения казны по регионам — то есть решения экономики.
- **Измерения покажут**, что после F2–F8 поток-писатель занят больше чем на 50–70% на пике у границы раунда, а экономический потолок при этом поднят. Тогда сначала S4 (конвейер внутри машины), и только потом шардирование по узлам.
- **Команда вырастет до нескольких команд**, каждой из которых нужна своя граница ответственности.

## 3. Язык ядра: Java против Rust

### 3.1 Что говорят источники

- **GC современной JVM.** JEP 439 «Generational ZGC» вошёл в JDK 21. Цель: «Pause times should not exceed 1 millisecond». Включается флагами `-XX:+UseZGC -XX:+ZGenerational`; планировалось сделать его сборщиком по умолчанию (openjdk.org/jeps/439). Это цель JEP, а не замер для Herd.
- **Прецеденты в обоих языках:**
  - LMAX (Java) — 6 млн заказов/с в одном потоке;
  - exchange-core (Java) — 5 млн оп/с;
  - Coinbase (Go и Java) — сквозная задержка меньше 50 мкс;
  - Hyperliquid (Rust) — ≈200 тыс. заказов/с, узкое место — исполнение.

  Это разные задачи, и напрямую сравнивать их нельзя. **Вывод:** опубликованные результаты верхнего класса есть на обоих языках; порядок величины определяет дизайн ядра, а не язык.
- **Микробенчмарки.** Pereira и др., SLE'17, таблица 4, нормировано к C:

  | Язык | Время | Память | Энергия |
  |---|---|---|---|
  | Rust | 1,04 | 1,54 | 1,03 |
  | Java | 1,89 | 6,01 | 1,98 |

  Это 10 CPU-задач и JVM 2017 года, не нагрузка «леджер + ввод-вывод».
- **Этот же стенд.** Java-сервер занимает 282 МиБ, Rust-сервис цепи — 14 МиБ (`the internal notes:35`). Задачи у них разные. **Вывод:** базовая память JVM заметно больше.
- **Нативный образ.** В GraalVM Native Image сборщик по умолчанию — Serial GC; G1 доступен только в Oracle GraalVM («Not available in GraalVM Community Edition»). **Вывод:** путь «Java, но мало памяти» через нативный образ обменивает качество GC на память.

### 3.2 Что говорит этот код

- **Объём:** `engine/src/main` — 3 619 строк, тесты `engine/` — 5 994 строки в 36 файлах (`wc`); 7 321 тест движка (`README.md:40`); сервер — 26 275 строк Java (`wc`).
- **Десятичная арифметика — часть контракта с цепью.** Выплаты считаются в `BigDecimal` с явными масштабами и режимами округления: `HALF_UP` в `GameEngine.java:48` и `GameService.java:914–915`, `DOWN` в `GameEngine.java:221`. Хеш итогов строится из этих чисел (`GameService.java:1002–1004`, `:1025`) и уходит в Chia. **Вывод:** вторая реализация обязана быть побайтно совместимой, иначе разойдутся хеши в цепи.
- **Команда.** «Алекс — senior Java-инженер, учит Rust» (`the project plan:67`). Rust уже стоит там, где окупается, — в сервисе цепи (`chain/`).

### 3.4 Рекомендация

**Java для ядра; Rust — на краю цепи, как сейчас.** Основания:
- ограничения L1–L8 одинаково сыграли бы и в Rust;
- 7 321 тест и десятичная семантика уже на Java;

- сильная сторона команды — Java.

Опция «всё на Rust» сохраняется через F4/F5: самодостаточный журнал и хеш состояния — это контракт, по которому любую вторую реализацию можно проверить реплеем.

### 3.5 Как решить измерением, а не мнением

**Бюджет записать заранее.** Ниже — предложение; конкретные числа решает Алекс:
- **B1 — пропускная способность:** поток ядра держит целевой пик (например, 10× средней нагрузки у границы раунда; среднюю взять из §6.2) и занят при этом не больше чем на 50%;
- **B2 — хвост:** p99,9 времени применения команды в ядре и p99,9 паузы GC — не больше 1 мс (по JFR; ориентир — цель JEP 439);
- **B3 — память:** байт на активного игрока и на открытую ставку (гистограмма кучи), RSS при 1 млн игроков;
- **B4 — рестарт:** загрузка снапшота + реплей хвоста — не больше 60 с (ориентир — «less than a minute» у LMAX).

**Протокол:**
1. **Сначала только Java.** Бенчмарк реплея (M2, §5.3) на синтетическом журнале через `EventApplier.over(...)` без БД. Сравнить G1 и `-XX:+UseZGC -XX:+ZGenerational`; снять JFR и async-profiler. Повторить после F2, F3, F6 и после перевода горячего пути на `long`.
2. **Только если Java не укладывается в бюджет** — прототип ядра на Rust, ограниченный горячими командами: резерв ставки, счётчики экспозиции, расчёт ставки. Он реплеит **тот же** журнал и обязан выдать **те же** хеши состояния на каждой контрольной точке (F5). Сравнивать на одной машине и одном журнале: команд/с на ядро, p99,9, RSS и потраченные дни разработки.
3. **Переходить только если** выигрыш Rust закрывает конкретный невыполненный пункт бюджета, которого Java не достигла настройкой, — а не «в принципе быстрее».

### 4.2 Следующие этапы и их триггеры

| Этап | Что | Триггер (измерение, которое оправдывает старт) |
|---|---|---|
| S1 | Последователи для чтений: второй процесс реплеит журнал (из Postgres по `seq`) и отвечает на чтения | M5: RPS чтений на пике больше ~50% того, что держит один узел, или p99 чтений выше бюджета |
| S2 | Горячий резерв записи: последователь, которого можно повысить; инструкция ручного переключения | Появились игроки, для которых простой важен, и записан SLO; или B4 не выполняется |
| S3 | Журнал вне Postgres: Chronicle Queue или Aeron Archive; Postgres остаётся для read-моделей | M3: p99 коммита пакета выше бюджета на целевой нагрузке, или Postgres (CPU, IO) — узкое место |
| S4 | Конвейер на несколько ядер в одной машине по образцу exchange-core: N шардов счетов (резерв и возврат баланса) + один глобальный этап риска и раунда (экспозиция, казна, предохранитель), Disruptor | Поток-писатель занят больше чем на 50–70% на пике после F2–F8, **и** экономический потолок (§6.2) поднят |

| S7 | Ядро на Rust | Java не выполняет бюджет §3.5 |
| S8 | Хеш итогов как корень дерева Меркла: доказательство для одного игрока, `results.json` не растёт с числом ставок; меняет формат записи в цепи — решение Алекса | Размер `results.json` за раунд мешает верификатору (измерить) |
| S9 | Несколько регионов / несколько казён | Только решение продукта и экономики |

### 4.3 Чего не делать сейчас

Kafka как ядро, кластер акторов, распределённый SQL, Raft, kernel bypass, переписывание ядра на Rust, нарезка на микросервисы. Ни у одного из этих шагов нет измерения-триггера.

## 5. Что мерить первым и как

### 5.1 Вопросы, на которые нужны числа

1. `t_hold` — время удержания write-блокировки на ставку, по частям: SELECT, INSERT, COMMIT, применение.
2. Время расчёта раунда на одну ставку и на раунд; сколько граница раунда блокирует ставки.
3. Стоимость применения одной команды в ядре без БД (замер 5,6 мкс на событие реплея уже есть, но он включает декодирование JSON).
4. Темп аллокаций и паузы GC (G1 против Generational ZGC).
5. Сколько RPS чтений держит один узел и как чтения влияют на p99 ставок.
6. Память на игрока и на открытую ставку.
7. Время рестарта в зависимости от длины журнала.

### 5.2 Инструменты

- **JFR** (встроен в JDK) — GC, аллокации, блокировки.
- **async-profiler** (Apache-2.0) — CPU и аллокации.
- **JMH** (GPL-2.0 по GitHub API, только в тестах) — микробенчмарки движка.
- **Gatling** (Apache-2.0) — HTTP-нагрузка; инструмент на JVM, знакомый команде. k6 — AGPL-3.0: как внешний инструмент пригоден, но Gatling ближе команде.
- **`pg_stat_statements`** и статистика WAL Postgres — время коммитов.
- **HdrHistogram** — перцентили (лицензия по API `NOASSERTION` — UNVERIFIED).

### 5.3 Сценарии

| # | Сценарий | Параметры | Что снимать |
|---|---|---|---|
| M1 | Движок без БД (JMH): `placeBet` / `replayBet` при N открытых ставках в раунде; `runRound` на N ставок | N = 10², 10³, 10⁴, 10⁵, 10⁶ | Время на операцию от N; должна быть видна O(N)-зависимость до F2 и её отсутствие после |
| M2 | Реплей синтетического журнала (`ReplayBench`) | 10⁶ и 10⁷ событий; реалистичная смесь: вход, ставки, отмены, расчёты 18 × 2 серий; G1 и ZGC | Событий/с, паузы GC p99,9, куча после реплея, RSS |
| M3 | Сквозной путь ставки по HTTP (Gatling) | Открытая модель с разгоном до ошибок; профиль «дедлайна»: например, половина ставок раунда — в последние 5 с до границы | p50/p99/p99,9 `placeBet`, потолок ставок/с, `t_hold` по частям, длительность `COMMIT`, JFR |
| M4 | Всплеск расчёта | R рынков × B ставок, все раунды кончаются на одной границе | Время расчёта; сколько ставки и чтения ждут блокировку |
| M5 | Чтения | V виртуальных зрителей, опрос раз в 2–3 с тех же ручек, что веб (`RpcResource.java:56`), параллельно с M3 | RPS чтений, влияние на p99 ставок |
| M6 | Память | 10⁵ и 10⁶ игроков с открытыми ставками | Байт на игрока и на ставку (гистограмма кучи) |

### 5.4 Где и как гонять

- **Стенд:** the bench box (Linux-сторона), по правилам общего ресурса — с арендой, отдельным compose-проектом, на полной мощности для генераторов нагрузки и последователей. Для самого ядра число ядер не важно: оно однопоточное.
- **Цепь:** chainsvc в режиме `C2_PUSH=0`, без публикации в цепь (`docker-compose.yml:103`: второй издатель не должен работать).
- **Не на VPS с демо:** там живые тестеры и единственный издатель (`the internal notes:37`).
- **Чтобы мерить ставки, а не вход:** вход тестовым кошельком вызывает chainsvc на каждую подпись, поэтому сессии засеять заранее (таблица `sessions`, `V1__init.sql`).
- **Лимиты на IP поднять в профиле нагрузки:** `RATE_LIMITED_METHODS` (`RpcResource.java:63`), лимит регистраций (`GameService.java:397`).
- **Каждый прогон записывать:** коммит, конфиг, железо, числа, файлы JFR.

## 6. Где цель сформулирована неточно или преждевременно

### 6.1 «Миллионы пользователей в секунду, все ставят» смешивает единицы

Пользователи — не ставки в секунду. Игрок ставит не больше одного раза на раунд серии рынка (R6). Арифметика:
- 1 млн одновременно активных игроков, каждый ставит на 3 рынках каждый 3-минутный раунд: 1 000 000 × 3 / 180 ≈ **16,7 тыс. ставок/с** в среднем;
- 10 млн игроков — ≈167 тыс./с;
- чтобы получить 1 млн ставок/с в среднем, нужно ≥8,3 млн игроков, и каждый ставит на **все** 18 рынков в **каждом** раунде обеих серий (18 × (1 + 1/5) ставки за 180 с ≈ 0,12 ставки/с на игрока).

Для сравнения: документация Hyperliquid называет ≈200 тыс. заказов/с для всего mainnet.

### 6.2 Потолок задаёт экономика, а не ядро

Константы кода:
- выпуск 100 млн PLAY (`GameService.java:195–196`);
- экспозиция одной стороны раунда рынка ≤ 0,25% × TREASURY / stress (`EconomyLimits.java:25`);
- крипто-корзина ≤ 1% × TREASURY по Σ(notional × stress) (`EconomyLimits.java:27`);
- значения stress по рынкам (`V12__economy_stage_b.sql:12–30`);
- минимальная ставка 100 PLAY (`LedgerBook.java:38`), минимальное плечо x2 (`Leverage.java:22`), то есть минимальный notional 200 PLAY.

**Расчёт (арифметика по константам, не замер).** Предельный случай: TREASURY = 100 млн и каждая ставка минимальна.

| Что | Значение |
|---|---|
| BTC: потолок одной стороны | 0,0025 × 10⁸ / 0,00817 ≈ 30,6 млн PLAY notional ≈ 153 тыс. минимальных ставок |
| Крипто-корзина (6 рынков), одна сторона | ≈86,6 млн |
| 6 рынков акций, индексов и сырья, одна сторона | ≈427,8 млн |
| 6 рынков шансов (stress 0,20), одна сторона | ≈7,5 млн |
| Все 18 рынков, обе стороны, 3-минутный раунд | ≈1,04 млрд notional ≈ **5,2 млн ставок** ≈ **29 тыс. ставок/с** в среднем |

Пятнадцатиминутная серия добавляет меньше: её stress умножается на коэффициент (`MarketEconomy.java:86–90`). Казна у игроков на руках меньше 100 млн, а при обычных ставках (например, 1 000 PLAY × x10 = 10 тыс. notional) потолок в 50 раз ниже.

Вывод: при текущих правилах D-92 лишние пользователи дают отказы `EXPOSURE_LIMIT_EXCEEDED`, а не принятые ставки. Принять на порядки больше можно только через решения экономики (эксперты по D-91):
- казна пропорционально обороту;
- лимит по **нетто**-экспозиции вместо брутто одной стороны (сейчас считается сторона, `GameService.java:2290–2293`);
- пулы без казны-контрагента (тотализатор).

Инфраструктура под «миллионы ставок в секунду» при нынешней экономике не будет загружена.

### 6.3 «Огромная скорость» в микросекундах продукту не нужна

Ставка закрывается в начале раунда, а раунд длится 3 или 15 минут. Справедливость у дедлайна уже обеспечена временем прихода (`RpcResource.java:108`, `GameService.java:750`). Нужно две вещи: не останавливать приём ставок и чтения на границе (L3) и выдерживать всплеск в последние секунды. Для сравнения: у Hyperliquid задержка заказа — медиана 0,2 с, p99 0,9 с. Kernel bypass, Aeron UDP и подобная техника — не про этот продукт. Бюджет задержки — десятки миллисекунд, а не микросекунды (предложение).

### 6.4 Первые стены — не в ядре

По коду и журналу состояния первыми упрутся:
- опросы чтений раз в 2–3 с (L6);
- расчёт на синхронной границе, который блокирует ставки (L3);
- наплыв входов под write-блокировкой (L8);
- testnet11: мемпул заполнен, публикация останавливалась 2026-10-14 (L10);
- одна VPS на 4 vCPU.

Ничего из этого выбор языка не решает.

### 6.5 «Развернуть всё на Rust» — дорогая опция, если держать её постройкой, и дешёвая, если держать её контрактом

Две реализации, которые разойдутся в десятичной арифметике, дают разные хеши итогов в цепи (§3.2). Вторая реализация — это вдвое больше тестов (7 321 тест движка на Java). Дешёвый способ держать опцию открытой — F4 и F5: журнал и хеш состояния как контракт.

### 6.6 «Скейлиться» и «очень мало ресурсов» тянут в разные стороны

Шардирование записи покупает горизонтальный рост ценой координации и дублирования. Один писатель — самый экономный по ресурсам путь до высокого потолка. Горизонтально стоит масштабировать то, чего реально много, — чтения (S1, S6).

### 6.7 Что преждевременно, а что нет

- **Сегодня:** ≈0,5 события/с на стенде (§1.6); пересборка при 91 тыс. событий — 510 мс (измерено).
- **Не преждевременно:** F1–F5. Они дешёвые, не меняют поведение и чинят то, что болит при любой нагрузке: рост памяти, время рестарта, нечистое применение событий.
- **Делать после базового замера M3:** F6–F8.
- **Преждевременно:** гонка Java против Rust, Kafka, кластер, Raft. Их ждут триггеры §4.2.
