# Раундовый движок: доменная модель, машина состояний, леджер, предложения

Разбор нового кода в `engine/` (пакеты `ledger`, `season`, `round` (дополнения), `crowd`, `rating`,
`player`, `game`), поверх уже существующей математики плеча/ликвидации
(`docs/research/hl_liquidation_math.md`, реализована в `crowdvsmarket.engine.margin`/
`round.PositionSimulator` — не менялась). Источник решений —
`the decision log` (Р-1…Р-21); при расхождении с `the project plan`
верны решения. Каждый пункт ниже, где применимо, помечен ссылкой на конкретное Р-N.

## 1. Доменная модель

```
crowdvsmarket.engine
├── margin, market, round.{Round,Position,PositionSimulator,Direction}   — день 1, не менялось
├── ledger    — PlayAmount, LedgerEntry(Type), PlayerAccount, SeasonRecord,
│               WithdrawalRequest/State, DepositRequest/State, OnChainWalletPort, LedgerBook
├── season    — Season (календарный месяц UTC)
├── round     — + RoundWindow, RoundClock, PositionSizing, RoundPrices/CandleSeriesRoundPrices,
│               Bet, BetBook, Position.openFromMargin(...)
├── crowd     — CrowdAccount
├── rating    — RatingBook
├── player    — PlayerIdentity
└── game      — GameEngine, RoundReport, PlayerRoundOutcome
```

**Единицы (Units, предложение — см. §4.1):** 1 PLAY ≡ 1 USD в математике позиции
(`crowdvsmarket.engine.margin`). В леджере PLAY хранится как целое число «mojo»,
1 PLAY = 1000 mojo (`PlayAmount`). Ставка игрока — это *ровно* initial margin позиции: размер BTC
подбирается (`PositionSizing`, 8 знаков после запятой) так, что
`round2(size * entry_price / leverage) == margin` — см. property-тест
`PositionSizingPropertyTest` (~6250 комбинаций цена×сэмпл, реальные цены из обеих фикстур плюс
синтетические крайние).

**Зависимости пакетов** — только вниз по списку выше (`game` зависит от всех, `ledger`/`season` ни
от чего внутри нового кода). `round`, `crowd` зависят от `ledger` только через `PlayAmount`
(значимый тип, не поведение).

## 2. Машина состояний раунда

Одна серия (`Interval.HOURLY` или `Interval.DAILY`) — один `GameEngine`. Окна раундов считает
`RoundClock` (чистая арифметика по UTC-миллисекундам, без календаря/DST — час и сутки делят UTC-сутки
ровно). Правило Р-19 — «всегда один идущий + один открытый для ставок раунд» — реализовано так, что
раунд N+1 открыт для ставок **весь** идущий раунд N: `RoundClock.next(windowN) == windowN+1`,
встык, без зазора.

```
                     RoundClock.next(window)
   ┌─────────────────────────────────────────────────────────┐
   │                                                           │
   ▼                                                           │
 BETTING (окно N)                                              │
   placeBet / cancelBet любое число раз, BetBook хранит         │
   максимум одну ставку на (round, player) — Р-13               │
   │                                                           │
   │ окно N наступает → GameEngine.runRound(windowN, prices)   │
   ▼                                                           │
 RUNNING → для каждой ставки:                                  │
   Position.openFromMargin(...) по цене открытия (Р-8)          │
   PositionSimulator.simulate(position, path) — реплей по       │
   OHLC пути раунда (одна свеча для HOURLY, ~24 для DAILY)      │
   │                              │                             │
   │ low/high пробили liq price   │ путь пройден без пробоя      │
   ▼                              ▼                             │
 LIQUIDATED                    SETTLED                          │
   payout = 0 (Р-7)               payout = max(0, margin+pnl)    │
   │                              │                             │
   └──────────────┬───────────────┘                             │
                   ▼                                             │
   LedgerBook.settleRound(...) — начисление payout, счётчики      │
   раунда/сезона (Р-9, Р-18); BetBook.clear(roundId)              │
   CrowdAccount.processRound(...) — независимо от игроков (Р-5)  │
                   │                                             │
                   └── следующее окно становится BETTING ─────────┘
```

Одна позиция игрока обрабатывается «изнутри» `PositionSimulator` (не менялся): это отдельная
маленькая машина `LIQUIDATED | SETTLED`, описанная в его javadoc (same-candle/gap-through правила).
Здесь она встроена в раунд как единственный шаг между `BETTING` и начислением.

**Почему одним вызовом, а не пошагово** (`RUNNING` не хранится как отдельное состояние объекта):
и для реплея фикстур, и для будущего live-оракула путь цен раунда становится известен целиком
только когда раунд фактически завершился (цена закрытия зафиксирована) — `GameEngine.runRound`
вызывается ровно один раз, когда это так, и делает open→monitor→settle атомарно. Живая версия
вызывает его в тот момент реального времени, когда окно раунда истекло, вместо перебора фикстуры в
цикле — интерфейс (`RoundPrices`) тот же.

Ставка (`Bet`) не хранит состояние сама по себе — её место в жизненном цикле определяется тем, в
какой структуре она сейчас лежит: `BetBook` (ещё не сыграна) → передана в `LedgerBook.settleRound`
(сыграна, `BetBook.clear` убрал её из `BetBook`) — состояние подразумевается местом, не полем,
как и `Round`/`Position` в коде дня 1.

### Машина состояний вывода/ввода PLAY (Р-6)

```
requestWithdrawal(amount) ──► REQUESTED (баланс уже списан — эскроу)
                                  │
                    ┌─────────────┴─────────────┐
                    ▼                             ▼
              confirmWithdrawal              failWithdrawal
              CONFIRMED (без изменений       FAILED (возврат amount
              баланса — списание уже         на баланс, откат
              случилось при REQUESTED)       season.withdrawn)

requestDeposit(amount) ──► REQUESTED (баланс НЕ тронут — PLAY ещё не пришли)
                                  │
                    ┌─────────────┴─────────────┐
                    ▼                             ▼
              confirmDeposit                  failDeposit
              (начисление amount,              (без изменений — PLAY
              CONFIRMED)                       так и не пришли, FAILED)
```

Обе машины — конечные автоматы `REQUESTED → {CONFIRMED, FAILED}` за интерфейсом
`OnChainWalletPort` (сам он не реализован в этом модуле — ончейн-сторона вне скоупа задачи; реальная
реализация в будущем Quarkus-сервисе вызывает `chia-wallet-sdk` и затем дергает
`confirm*/fail*` как callback).

## 3. Операции леджера (`LedgerBook`)

Однопоточный, функциональное ядро/мутируемая оболочка: каждый `PlayerAccount`/`SeasonRecord` —
неизменяемый снимок, целиком заменяемый при любой мутации; каждая мутация также добавляет одну
`LedgerEntry` в append-only лог (`entries()`).

| Операция | Что делает | Тип(ы) записи |
|---|---|---|
| `ensureSeasonPack(player, now)` | Ленивая выдача стартового пакета на первую активность игрока в сезоне `Season.of(now)` (Р-2/Р-12); при смене сезона фиксирует баланс ДО пакета как `baselineBalance` (Р-16, Р-18) | `STARTER_PACK` |
| `reserveStake(player, round, stake, now)` | Проверка минимальной ставки (Р-12) и `stake <= баланс`, затем списание | `STAKE_DEBIT` |
| `refundStake(player, round, stake, now)` | Возврат ставки при отмене/замене до старта раунда (Р-13) | `STAKE_REFUND` |
| `settleRound(player, round, payout, directionCorrect, now)` | Начисление payout (0 при ликвидации — Р-7), инкремент счётчиков раунда/направления сезона (Р-9/Р-18) | `SETTLEMENT` |
| `requestWithdrawal`/`confirmWithdrawal`/`failWithdrawal` | См. машину состояний выше (Р-6) | `WITHDRAWAL`, `WITHDRAWAL_REFUND` |
| `requestDeposit`/`confirmDeposit`/`failDeposit` | См. машину состояний выше (Р-6) | `DEPOSIT` |

**Баланс никогда не уходит в минус**: любая операция, которая довела бы баланс до отрицательного,
кидает исключение ДО записи в лог (проверено в `LedgerBookTest`, а на масштабе месяца —
в `MonthLongHourlySimulationTest`).

**Инвариант консервации** («дом» — единственный источник новых PLAY и единственный, кто их сжигает):
единственное, что создаёт PLAY внутри игры — стартовые пакеты и чистый выигрыш при расчёте раунда;
единственное, что уничтожает — чистый проигрыш при расчёте, включая полную потерю ставки при
ликвидации (Р-7). Пополнение/вывод переносят PLAY через границу ончейн/оффчейн, не создавая и не
уничтожая их внутри игры. `MonthLongHourlySimulationTest` проверяет это двумя независимыми
способами: (1) реплей лога `entries()` воспроизводит текущий баланс каждого игрока; (2) итоговый
баланс всех игроков равно (выданные пакеты) + (сумма `payout - stake` по каждой сыгранной ставке),
где вторая сумма накоплена во время симуляции из отчётов `GameEngine.runRound`, а не из лога леджера
— то есть по коду, независимому от внутренней бухгалтерии `LedgerBook`.

## 4. Предложения (с обоснованием)

Отмечены `предложение` в коде и здесь; ни одно не переопределяет зафиксированное решение —
только заполняет то, что решения оставляют открытым.

### 4.1 Единица леджера: 1 PLAY = 1000 mojo

Решения фиксируют название токена (PLAY) и то, что это CAT2 (`the project plan` §3), но не масштаб
внутриигрового целочисленного представления. Взят масштаб 1000 (а не родной для Chia 10^12
mojo/XCH): вся математика позиции работает по 2 знакам после запятой (центы), 1000 этого достаточно
без риска потери точности от наивной double/float-арифметики где-то выше по стеку, и держит целые
суммы (пакет 10 000, минимальная ставка 100) точными. Реальный ончейн-масштаб CAT2 на testnet11 —
отдельный вопрос уровня блокчейна, см. открытые вопросы ниже.

### 4.2 Точность размера BTC — 8 знаков (сатоши)

`PositionSizing.SIZE_SCALE = 8`: стандартное деление BTC, и ошибка округления
(не больше `0.5×10⁻⁸ × цена` в `size × price`, дальше только уменьшается делением на плечо ≥ 2)
остаётся много меньше половины цента для любой реалистичной цены BTC — доказано
`PositionSizingPropertyTest` на реальных ценах фикстур плюс синтетических крайних.

### 4.3 Границы раунда — UTC, выровнены по свечам Hyperliquid

Р-19 фиксирует, что часовой раунд идёт по часовым, дневной — по суточным (00:00 UTC) границам, но
не называет конкретный часовой пояс. Взят UTC (as-is у Hyperliquid `candleSnapshot`, см.
`fixtures/PROVENANCE.md`) — иначе понадобилось бы либо реализовывать интерполяцию цены на границах
не совпадающих с свечами, либо вводить отдельный часовой пояс без источника в `docs/`.

### 4.4 Сезон — календарный месяц UTC

Р-10/Р-16 фиксируют длину сезона (месяц), не календарь/часовой пояс. Взят тот же UTC, что и у
границ раунда (§4.3) — граница сезона тогда всегда совпадает с границей часового раунда, не
разрезая ни один раунд пополам.

### 4.5 Порог рейтинга N = 10 раундов (по умолчанию, настраиваемо)

Р-9/Р-18 фиксируют, что порог существует («рейтинг можно накрутить» без него), не его значение.
`RatingBook.DEFAULT_ROUNDS_THRESHOLD = 10` — предложение без источника в данных; конструктор
`RatingBook` принимает любое N.

### 4.6 «Пророки»: направление против sign(close − open), независимо от ликвидации

Р-18 называет метрику («доля раундов с угаданным направлением»), не её точную формулу при
ликвидации. Взято: направление засчитывается по знаку движения цены независимо от того, дожила ли
позиция до конца раунда (ликвидированный игрок мог всё равно угадать сторону — плечо это отдельный,
уже наказанный балансом риск). Плоские раунды (close == open) исключены из знаменателя — иначе
монетка «оба варианта неверны» искусственно занижала бы точность всем, кто играл в такой раунд.

### 4.7 Отображаемое имя: ник + первые 6 / последние 4 символа адреса

Р-15 фиксирует состав (ник + сокращённый адрес), не формат сокращения. Взят распространённый
паттерн кошельков (`xch1qp…mqqqxw`); адреса короче 14 символов показываются целиком — сокращать
было бы нечего.

### 4.8 Списание при выводе — в момент заявки, не при подтверждении

Р-6 фиксирует состояния (`requested → confirmed/failed`), не момент списания баланса. Взято:
баланс списывается уже при `REQUESTED` (эскроу) — иначе один и тот же баланс можно было бы указать
в нескольких одновременных заявках на вывод. Это упрощение однопоточной модели этого модуля; в
Quarkus-сервисе (параллельные запросы) может понадобиться отдельная блокировка на уровне игрока —
вне скоупа этого движка.

### 4.9 Изменение ставки — отмена-и-новая-заявка, без отката при ошибке

Р-13 фиксирует право менять ставку до старта раунда. `GameEngine.placeBet` сначала возвращает
старую ставку на баланс, потом резервирует новую — в этом порядке (не наоборот) увеличение ставки
вплоть до всего высвобождённого баланса не отклоняется ошибочно (реальный баг ранней версии, пойман
`GameEngineRoundLifecycleTest`). Если новая ставка сама по себе невалидна (ниже минимума/выше
баланса), старая ставка не восстанавливается — итог виден в балансе и `BetBook` (нет ставки на этот
раунд), без частичного «отката» ради простоты toy-money MVP.

## 5. Открытые вопросы Алексу

1. **Порог N (Р-9/Р-18) — общий на игрока или отдельно по сериям HOURLY/DAILY?** Сейчас одна
   `SeasonRecord` на игрока считает раунды обеих серий вместе (если у игрока будет открыт `GameEngine`
   и на HOURLY, и на DAILY). Нужно ли считать и сравнивать отдельно — открыто.
2. **Реальный ончейн-масштаб CAT2 PLAY на testnet11** (mojo-на-PLAY константа) — нужен до дня 2
   (выпуск CAT), чтобы слой конвертации между внутриигровым `PlayAmount` (1000 mojo/PLAY, §4.1) и
   ончейн-балансом был точным, без округления в обе стороны.
3. **Списание при заявке на вывод (§4.8)** — подтвердить, что баланс должен блокироваться сразу при
   `REQUESTED`, а не оставаться доступным до `CONFIRMED`.
4. **«Пророки» при ликвидации (§4.6)** — подтвердить, что угаданное направление засчитывается
   независимо от ликвидации (плечо наказывается балансом, не рейтингом), а не только доигранным до
   конца раундам.

## 6. Волна 2 (security-фиксы по тестам, перед ревью критика) — 2026-09-26

Правит находки второго раунда тестирования (`requestWithdrawal("-5000.000")` минтил PLAY). Затронуты
только `engine/ledger` — аддитивно, ни один существующий публичный метод не меняет сигнатуру.

**`PlayAmount.requirePositive(String what)`** (предложение) — бросает `IllegalArgumentException`,
если `mojos <= 0`; возвращает `this` для fluent-использования на месте вызова. Единственный новый
универсальный «денежный» guard движка.

**Где guard реально стоит, а где — намеренно нет.** `LedgerBook.reserveStake` зовёт его первой
строкой (безопасно: `MIN_STAKE > 0` и так уже отбрасывал любой неположительный stake во всех
существующих событиях `BetPlaced` — исторических нарушителей нет). `LedgerBook.requestWithdrawal`/
`requestDeposit` — **намеренно не зовут** `requirePositive` внутри себя, хотя это тот самый метод,
где родился баг: `debit(amount)` негирует `amount` перед применением, так что `amount=-5000` тихо
стало кредитом `+5000` после автоподтверждения (`GameService` подтверждает вывод сразу же, реального
моста на chain нет, §3). Причина — эти два метода одновременно и «применяют новую живую команду», и
«переигрывают уже случившееся историческое событие» при рестарте (`EventApplier`/
`EngineRebuildService`, один и тот же код path для обоих, по замыслу этого движка). Уже
персистентное события `WithdrawalRequested(amountMojos=-5000000)` — то самое, что породил
эксплойт до этого фикса — задача прямо запрещает менять или удалять; если бы guard стоял внутри
`requestWithdrawal`, каждый следующий рестарт падал бы на реплее именно этого события
(`IllegalArgumentException`, необработанное, в цикле `EngineRebuildService.rebuild()`) — то есть сам
деплой этого фикса на стенд, где баг уже случился, ронял бы сервер на первом же рестарте, ещё до
того, как оператор успел бы применить коррекцию. Поэтому guard стоит на уровне команды —
`GameService.requestWithdrawal`/`requestDeposit`, до того как событие вообще создаётся и
персистится (server_design.md §14) — а не на уровне «применить уже решённое», которое обязано
пережить рестарт буквально как было.

**`LedgerEntryType.OPERATOR_CORRECTION`** (предложение, аддитивно) — тип записи для
`LedgerBook.reverseWithdrawalEffect` (см. ниже); не в `contract.ts`, та же ситуация, что и с
`INVALID_NICKNAME`/`RATE_LIMITED` на стороне сервера.

**`LedgerCorrection`** (новый record: `correctionId, playerId, delta, reason, relatedWithdrawalRequestId,
atEpochMs`) + `LedgerBook.corrections()` — публичный, реплеимый журнал операторских коррекций,
аналог `entries()`/`CrowdAccount.history()` (тоже только в памяти, тоже восстанавливается репleем,
отдельной read-model таблицы не нужно).

**`LedgerBook.reverseWithdrawalEffect(playerId, originalAmount, originalSeason, reason,
relatedWithdrawalRequestId, now)`** — операторская коррекция (паттерн Р-32/Р-43): применяет
`originalAmount` к балансу как есть (ровно обратное тому, что `debit(originalAmount)` применил
изначально — повторное отрицание восстанавливает исходный знак) и `originalAmount.negate()` — к
`withdrawn` того сезона, в котором произошёл исходный вызов (`originalSeason`, а не сезон на момент
коррекции — иначе коррекция после смены сезона испортила бы не тот `SeasonRecord`). Умышленно **не
ищет** `relatedWithdrawalRequestId` в `withdrawals` — вызывающий (`GameService.reverseWithdrawal`)
читает текущие `amount`/`requestedAtEpochMs` заявки на вывода ОДИН РАЗ, в момент команды, и передаёт
их сюда уже готовыми значениями. Это делает реплей самой коррекции независимым от того, реплеилось
ли исходное (потенциально уже нарушающее новый guard) событие успешно — коррекция описывает себя
полностью сама. В отличие от `failWithdrawal`, не требует состояния `REQUESTED` (в этом сервере
вывод подтверждается мгновенно, `REQUESTED` никогда не задерживается) и не трогает состояние самой
заявки — исторический факт, включая баг, который его породил, остаётся как есть. Защита от повторного
применения — по `relatedWithdrawalRequestId` внутри уже накопленных `corrections()` (это новый
список, у него нет исторических нарушителей, так что проверка безопасна и при живом вызове, и при
реплее).

**`Season.parse(String id)`** (предложение, аддитивно) — обратная операция к `Season.id()`
(`"YYYY-MM"`), нужна `EventApplier`, чтобы восстановить `Season` из `GameEvent.WithdrawalReversed`'а
собственного `originalSeasonId` при реплее.
