## 1. Что инструмент проверяет — и что нет

**Проверяет:**

1. **Родословную синглтона** — от launcher-монеты вперёд по публичному API `coinset.org`
   (`get_coin_record_by_name`/`get_coin_records_by_parent_ids`/`get_puzzle_and_solution`, без
   ключей, без нашего сервера) — что это одна цепочка без развилок (у каждой монеты ровно один
   ребёнок).
2. **Каждый `CREATE_PUZZLE_ANNOUNCEMENT` каждого спенда** — раскодирован (реальным CLVM-рантаймом
   `chia_rs`, прогоном on-chain puzzle_reveal против его же on-chain solution — не эмуляцией) в
   6-элементный список `(seq, ts, priceCents, resultsHash, sourceFlag, sourceTs)` либо, начиная с
   формата записи v2, в 7-элементный с седьмым `asset` — индексом рынка в публичном реестре (для BTC,
   индекс 0, седьмого элемента нет: его announcement побайтно такой же, как всегда). Любая другая форма
   (3-элементное сообщение недели 1, 5 или 8 элементов, `asset` вне `0..2^32-1`, `resultsHash` не из 32
   байт) — не запись и идёт в «неразобранные».
3. **Учёт по `seq`**: первое появление (высота + монета), повторы (совпадающие поля **включая `asset`** — не
   проблема, это ожидаемый повторный паблиш из durable-очереди `chainsvc` после гонки reconciliation;
   различающиеся поля под тем же `seq`, пусть даже только `asset` — **CONFLICT**, две разные «истины» под
   одним номером), и разрывы в последовательности `seq` (номер, для которого якорь так и не попал в цепь).
4. **(при `--stand-url`) Сверку со стендом**: для каждого `seq` из цепи в области проверки находит
   соответствующий раунд через публичный API стенда (журнал записей, а для стенда без него — обход раундов,
   см. §2 и §7), забирает его `GET /api/rounds/{id}/results.json` и проверяет `sha256(байты) == resultsHash`
   из цепи, `closePriceCents == priceCents` из цепи и что индекс актива в цепи совпадает с индексом, который
   стенд приписывает раунду (и что его реестр сопоставляет этот индекс рынку раунда).

**Не проверяет** (явно, а не по умолчанию):

- Что опубликованная цена сама была честной ценой BTC — доверие ключу оператора и Hyperliquid как
  источнику это осознанный, задокументированный компромисс (D-11, `the project plan` §2), а не то, что
  проверяет этот инструмент.
- Что выплаты внутри `results.json` посчитаны верно движком — это зона юнит-тестов `engine/`.
- Подписи `AGG_SIG_ME` каждого спенда — публичная цепь уже отвергла бы любой спенд, не прошедший
  эту проверку, до его подтверждения; проверять это заново здесь означало бы просто повторно
  доверять тем же публичным данным цепи, которые инструмент и так читает.

## 2. Как раунд сопоставляется с `seq`

**Основной путь с v2** — журнал записей стенда `GET /api/oracle/records?fromSeq=&limit=` (§7): тонкое
чтение таблицы `oracle_records` стенда, покрывает все рынки и все раунды, не только достижимые обходом. Всё
ниже в этом разделе — **запасной путь для стенда без журнала** (ответ 404): он работает только для BTC и
был единственным в первой версии (на старом стенде работает без изменений).

Готового `GET /api/rounds/by-seq/{seq}` в проекте нет; запасной путь находит соответствие сам:

- `roundId` детерминирован: `RoundWindow.roundId() = "<код интервала>-<startMs>"`
  (`engine/src/main/java/crowdvsmarket/engine/round/RoundWindow.java`), где `startMs` идёт
  фиксированным шагом от момента первого старта стенда (D-19: «всегда один идущий и один открытый
  для ставок раунд каждого типа»).
- Инструмент публичным `POST /api/rpc/rounds {"args":["HOURLY"]}` (и `"DAILY"`) узнаёт окно
  **текущего** идущего раунда (без всякой сессии — `round`/`rounds` не входят в `requireSignedIn`
  в `RpcResource.java`) — это даёт один заведомо верный `startMs` и шаг серии
  (`endMs − startMs`).
- Дальше шагает `roundId` назад на этот шаг и на каждом шаге зовёт публичный
  `POST /api/rpc/round {"args":["<roundId>"]}`. Любой ещё сохранённый в базе стенда
  settled-раунд отвечает DTO с полем `oracleAnchor: {seq, state, height}`
  (`Rounds.RoundSettled.oracleAnchor`, собирается из
  `OracleRecordRepository.findAnchorByRoundId` — колонка `oracle_records.round_id` там уже есть,
  просто не выставлена отдельной ручкой) — это и есть публичное сопоставление `seq ↔ roundId`, только
  не оформленное как отдельный lookup. Инструмент останавливает обратный обход серии на первом
  `roundId`, на который стенд отвечает 404 (реально до начала истории стенда либо гонка с ещё не
  досчитанным раундом) — горстка старых `seq` за этим горизонтом не считается находкой, это просто
  история, которую инструмент не стал угадывать.

**Предложение**, если когда-нибудь захочется сделать это отдельной первоклассной ручкой вместо
производного обхода: `GET /api/rounds/by-seq/{seq}`, тот же набор полей (`roundId`, `oracleAnchor`,
`resultsHash`), тонкий `SELECT` над уже существующей колонкой `oracle_records.round_id` — новое
состояние не нужно. Ничего в этом инструменте от этого предложения не зависит — обход выше уже
даёт полное и верное сопоставление для каждого раунда, который стенд ещё хранит.

## 3. Как запустить

Зависимость — один пакет, не входящий в stdlib: [`chia_rs`](https://pypi.org/project/chia_rs/),
официальная реализация CLVM от Chia Network с питоновской обвязкой (используется только чтобы
прогнать on-chain puzzle_reveal каждого спенда против его же on-chain solution — чистое вычисление
над уже публичными данными, без ключей и без собственных сетевых вызовов). Есть готовые wheel'ы
вплоть до самых новых Python (проверено — ставится и на Python 3.14).

```bash
cd tools/verify-oracle
pip install -r requirements.txt

# только цепь (testnet11 по умолчанию):
python3 verify_oracle.py c5cb79a5ea20fb66a29c63867806dec4d1120fa002b386c6033fec09b9cdeb20

# цепь + сверка с локальным стендом (CONTRIBUTING.md):
python3 verify_oracle.py c5cb79a5ea20fb66a29c63867806dec4d1120fa002b386c6033fec09b9cdeb20 \
    --stand-url http://localhost:8480 --json-out result.json

# строго: пропуски и несопоставленные seq в области проверки тоже дают код 1;
# отвечать за стенд только с seq 1146 (по умолчанию — с firstSeq самого стенда):
python3 verify_oracle.py c5cb79a5ea20fb66a29c63867806dec4d1120fa002b386c6033fec09b9cdeb20 \
    --stand-url http://localhost:8480 --strict --from-seq 1146
```

`c5cb79a5ea20fb66a29c63867806dec4d1120fa002b386c6033fec09b9cdeb20` — launcher id оракула этого
проекта (неделя 1, `chain/README.md`); первый аргумент — любой launcher id любого синглтона на
выбранной сети (`--network mainnet`), инструмент не завязан на этот конкретный проект.

## 4. Как читать вывод

- В stdout — человекочитаемая сводка; `--json-out FILE` дополнительно пишет полный JSON (каждое
  поколение, каждое announcement, полная история каждого `seq`, детали сверки со стендом).
- **Здоровый** прогон: `CONFLICTS: 0`, `Gaps in the seq sequence: 0`, и (при `--stand-url`)
  `Mismatches: 0`. Ненулевые `Benign duplicates` — это нормально (см. §1). Последняя строка вывода —
  `VERDICT: OK (exit 0)` или `VERDICT: PROBLEMS FOUND (exit 1)` с перечнем причин.
- Код выхода (с v2): `0` — чисто; `1` — прогон завершился и нашёл проблему: CONFLICT, расхождение со
  стендом, ошибка линии (развилка, обход, оборванный `--max-generations`, спенд, который не удалось
  раскодировать — проверка неполна, это не «ок»), а со `--strict` ещё и пропуск `seq` или несопоставленный
  `seq` внутри области проверки; `2` — прогон не смог завершиться: coinset или стенд недоступны либо
  отвечают не тем (**сетевая ошибка — всегда 2 и сообщение в stderr, не traceback и не 1**), неверные
  аргументы, не установлен `chia_rs`, launcher-монеты нет или она не потрачена. В первой версии
  неперехваченная сетевая ошибка давала код 1 — тот же, что «нашёл расхождение».
- Одно раннее announcement (самый первый спенд синглтона, неделя 1, ещё до D-41) использует
  сверх-старый 3-элементный формат без `resultsHash` — инструмент честно показывает его отдельно
  под `Unparsed announcement-shaped conditions`, а не путает с коллизией `seq`. Это ожидаемая
  история эволюции формата, не находка. Раскодировано вручную для протокола: `(priceCents=8 396 500,
  ts=1790353493, seq=1)` — то же самое первое announcement недели 1, что задокументировано в
  `the project plan` §1 («блок 4 735 705, price 8 396 500 ¢, ts 1790353493, seq 1»).

## 7. Верификатор v2 (2026-10-01)

**Зачем.** Формат записи v2 (`docs/research/markets_architecture.md` §7 п. 2; `chain_service.md` §16): announcement
не-BTC записи получает седьмой элемент `asset`. Верификатор первой версии принимал только ровно 6 элементов,
остальное уходило в «неразобранные» — `seq` рынков кроме BTC исчезли бы из учёта и показались бы пропусками,
а код выхода ничего бы не заметил. Заодно закрыты дефекты, найденные разведкой 2026-10-01 при чтении кода:
неперехваченная сетевая ошибка давала код выхода 1 (тот же, что «нашёл расхождение»); код выхода игнорировал
пропуски; `seq`, которого нет на стенде, был молчаливым списком; сопоставление раунда с `seq` было зашито
на два ряда BTC.

### 7.1 Что изменилось

| | первая версия | v2 |
|---|---|---|
| форма announcement | ровно 6 элементов | 6 (asset 0) или 7 (`asset` > 0); остальное — «неразобранные»; нужны атомы, хеш — 32 байта, `seq` ≥ 0, `asset` в `0..2^32-1`, правильный список (строже Rust-декодера chainsvc, который игнорирует лишние элементы: это инструмент аудитора, «не знаю такую форму» — правильный ответ) |
| дубликат / конфликт | по 6 полям | по 7 полям: 6-элементная запись и 7-элементная с явным `asset` 0 — одна запись; расхождение только в `asset` — CONFLICT (в выводе перечислены различающиеся поля) |
| `seq → раунд` | обход раундов, только BTC | журнал `GET /api/oracle/records` (все рынки); обход — запасной путь для стенда с ответом 404 |
| проверка раунда | хеш, цена закрытия | + индекс актива в цепи = индекс стенда; реестр стенда сопоставляет его рынку раунда; `market` в `results.json`, если есть, = рынок из журнала |
| `seq`, которого нет на стенде | молчаливый список | «до базы этого стенда» (`seq` < `firstSeq`: проверяются только по цепи) и «несопоставленные в области» (внутри области: список и предупреждение, код 1 со `--strict`) |
| пропуски | печатались, на код выхода не влияли | печатаются; внутри области проверки со `--strict` — код 1 |
| ошибка линии (развилка, обрыв по `--max-generations`, нераскодируемый спенд) | печаталась, код 0 | код 1 |
| сеть / HTTP | traceback, код 1 | сообщение в stderr, код 2 |
| аргументы | не проверялись | launcher id — 64 hex, `--from-seq` ≥ 0 и т. д.: код 2 |
| тесты | не было | `tools/verify-oracle/test_verify_oracle.py`, офлайн |

### 7.2 Область проверки, `--from-seq`, `--strict`

Область проверки — диапазон `seq`, за который прогон спрашивает со стенда: `--from-seq N`, иначе `firstSeq`
самого стенда (начало его базы), а для старого стенда без журнала — наименьший `seq`, который он
сопоставил; без стенда — вся цепь. `seq` ниже области — «опубликовано до базы этого стенда» (или «ниже
`--from-seq`»): проверяются только по цепи (линия, дубликаты, конфликты, пропуски), сверки с раундом нет, и
это не расхождение. Внутри области: **несопоставленный** `seq` — цепь держит announcement, о котором стенд
ничего не знает (чужая или устаревшая запись в эпохе этого стенда); **пропуск** — `seq`, который линия
перепрыгивает (учитывается и начало области: `seq` с начала области до первого найденного). Пропуски ниже
области относятся к прежней эпохе и не валят строгий прогон. Записи, которые стенд поставил в очередь, а в
цепи их ещё нет, — справочный список, не отказ. Сводка и вердикт печатаются в конце вывода.

### 7.3 Контракт со стендом

## 8. Серверная сторона v2 (2026-10-02): `asset` на проводе, пол `seq`, реестр и журнал записей

Это «FIXED INTERFACE O» (`docs/research/markets_architecture.md` §7 п. 1, 4–6) со стороны Java-сервера — то, что
верификатор из §7 читает у стенда и что отправляет chainsvc из `chain_service.md` §16. Код (всё под
`server/src/main/java/crowdvsmarket/server/`): `chain/ChainSvcClient.java` (+ `ChainSvcRestClient`,
`ChainSvcClientImpl`), `chain/OracleAssetGuard.java`, `chain/ChainOracleSeqGate.java`,
`scheduler/OraclePublisherService.java`, `scheduler/OracleReconciliationService.java`,
`persistence/OracleRecordRepository.java`, `persistence/ServerMetaRepository.java`,
`api/MarketRegistryResource.java`, `api/OracleRecordsResource.java`. Миграции нет: все поля журнала уже лежат в
`oracle_records` (V1, V2, V7).

### 8.1 Что уходит в chainsvc

- Каждая строка `oracle_records` уходит в `POST /v1/oracle/records` с полем `asset` — индексом рынка в реестре
  (`markets.oracle_index`, BTC = 0). Ключ шлётся **всегда**, у BTC тоже (`"asset": 0`): chainsvc старше формата
  2 неизвестный ключ молча отбрасывает (`OracleRecordDto` без `deny_unknown_fields`,
  `chain/c2-svc/src/oracle/types.rs`), а chainsvc формата 2 читает; announcement у `asset = 0` остаётся
  6-элементным и побайтно прежним, у `asset > 0` получает седьмой элемент (`chain_service.md` §16.2).
- `priceCents` записи — цена лота в сотых, то есть `сырая цена × 10^priceDecimals` рынка
  (`markets_architecture.md` §6; `priceDecimals` — в реестре, §8.4); `resultsHash` — `0x` + sha256 байтов
  `results.json` раунда; `source` — `live` или `replay`; `seq` — один общий счётчик на все рынки.
- Раньше `OracleRecordRepository.pending()` отдавал только `asset_index = 0`, чтобы запись не-BTC рынка
  никогда не ушла без `asset` и не стала бы на цепи «ценой BTC». Фильтр снят: решение «можно ли сейчас
  отправить» принимает `OraclePublisherService` по тому, что chainsvc сообщил о себе (§8.2).

### 8.2 Запись другого рынка и chainsvc без формата 2: поток встаёт, обгона нет

**Правило.** Запись с `asset > 0` отправляется только если chainsvc **только что** (живым `GET
/v1/oracle/status`, не из кэша `OracleStatusCache`, который стареет до 5 с — в это окно откат chainsvc на старый
образ ещё считался бы форматом 2) ответил `recordFormat >= 2`. «Не знаем» — это «нет»: chainsvc не отвечает,
в статусе нет `recordFormat` (старый chainsvc — формат 1, как требует `chain/c2-svc/src/oracle/types.rs`), или
`recordFormat < 2`. Запись, у которой `asset = 0`, статуса не требует: BTC-записи принимает любой chainsvc.

**Решение: `seq` — один упорядоченный поток, и при отказе он останавливается на первой удерживаемой записи.**
Уходят записи до первой записи с `asset > 0`; она и всё после неё (в том числе более поздние BTC-записи)
ждут (`OraclePublisherService.sendable`). Альтернатива — пропустить вперёд BTC-записи, обогнав удерживаемую.
chainsvc сам это допустил бы: `QueueFile::enqueue` принимает запись в любом порядке, а запись ниже своей
«ватерлинии», которую он не видел, берёт как позднюю (`chain/c2-svc/src/oracle/queue.rs`,
`chain_service.md` §10.3 и §10.7), так что по правилам очереди обгон безопасен для самого chainsvc. Но на
цепи при обгоне в наборе `seq` появляются дыры — на всё время удержания и навсегда, если chainsvc так и не
обновят, — а публичный верификатор не может отличить дыру, которую мы оставили сами, от якоря, который
потерялся (§1 п. 3, `--strict`), а именно это он и должен различать. Остановка потока ничего не теряет, кроме
времени: все строки остаются в `oracle_records` и уходят подряд по возрастанию `seq`, как только chainsvc
скажет «формат 2». Цена решения — пока chainsvc старый, не уходят и BTC-записи после первой удерживаемой; это
ошибка порядка выкладки (`chain_service.md` §16.2: сначала chainsvc, потом сервер), и о ней сервер пишет в лог
(раз в минуту: сколько записей, с какого `seq`, какой формат).

Что видно снаружи, пока поток стоит: предупреждение в логе сервера и строки в `GET /api/oracle/records` со
`state: "unknown"` (верификатор перечислит их как «записи, которые стенд поставил в очередь, а в цепи их нет»);
`serverInfo().oracle.pendingRecords` этого не показывает — пока chainsvc отвечает, там его собственная очередь, а
удерживаемые строки в неё не попадали. Игре это не мешает — подтверждение в цепи никогда не блокировало игру.

### 8.3 Пол `seq`

Источник: `markets_architecture.md` §7 п. 4. Один синглтон оракула живёт в цепи навсегда, а база сервера может
быть новой: счётчик `seq` на пустой базе начинается с 1, хотя цепь уже держит 1..N, и каждая такая запись была
бы отвергнута как повтор, а chainsvc просто игнорирует уже известный `seq`, даже с другим содержимым
(`chain_service.md` §16.9) — запись молча не опубликовалась бы никогда.

- `ServerMetaRepository.raiseOracleSeqTo(floor)` поднимает счётчик до `floor` и **никогда не опускает**
  (`floor` не больше счётчика — ничего не меняется); своя транзакция, тот же замок строки, что у резервирования
  `seq` расчётом раунда (`reserveOracleSeqRange`), поэтому подъём не вклинивается между чтением и записью
  счётчика; `floor` вне `0..2^53` — `IllegalArgumentException` (такой ответ может быть только испорченным).
  Следующий выданный `seq` — `floor + 1`: пустая база и цепь на 1145 дают первый `seq` 1146.
- `ChainOracleSeqGate` (реализация `OracleSeqGate`, которую планировщик спрашивает перед расчётом и отменой)
  каждые 5 с (`@Scheduled`, `concurrentExecution = SKIP`) читает статус chainsvc **сам** и поднимает счётчик до
  `maxKnownSeq`; поднимает снова, когда поздний статус показывает больше (другой писатель, chainsvc дочитал
  цепь после первого ответа).
- `herd.oracle.require-seq-floor` (переменная `HERD_ORACLE_REQUIRE_SEQ_FLOOR`, по умолчанию `false`; стенд и
  VPS — `true`, `docker-compose.yml`, `deploy/compose.prod.yml`): при `false` `open()` всегда `true`, счётчик
  всё равно поднимается, когда статус читается; при `true` `open()` становится `true` после первого успешного
  чтения статуса и подъёма счётчика и остаётся `true` (chainsvc, который пропал позже, игру не останавливает).
  Пока закрыт, планировщик (его вызов `OracleSeqGate.open()` — в срезе планировщика, не здесь) ничего не
  рассчитывает и не отменяет, раунды копятся и догоняются после открытия.
- Статус **без** `maxKnownSeq` (chainsvc старше формата 2) обязательный вход **никогда** не открывает: пола
  нет, а выдумывать его — значит снова проиграть историю; в лог раз в минуту пишется причина.

### 8.4 Два публичных эндпоинта

Оба — `GET`, без сессии, `Cache-Control: no-store`; nginx стенда (`web/nginx.conf`) и Caddy VPS
(`deploy/Caddyfile`) пропускают весь `/api/*` к серверу без изменений, ограничения частоты на них нет (верификатор
листает журнал подряд страницами по 1000).
Неверный запрос — `400` в обычном конверте `{"error":{"code","message"}}`, **никогда не `404`**: верификатор читает
404 на `/api/oracle/records` как «стенд без журнала» и уходит в обход раундов только для BTC.

**`GET /api/markets/registry.json`** — все рынки, которые когда-либо были в списке (закрытые тоже), по индексу:

```json
[{"index":0,"id":"BTC","kind":"PERP","symbol":"BTC","priceDecimals":2,"source":"hyperliquid","sourceRef":"BTC","listedAtMs":0},
 {"index":1,"id":"T_OREC1","kind":"PERP","symbol":"ETHJ","priceDecimals":3,"source":"synthetic","sourceRef":"T_OREC1","listedAtMs":1790896651399}]
```

`index` — то, что запись несёт на цепи как `asset`; индекс только растёт и не переиспользуется, поэтому запись
реестра после листинга не меняется (`DbMarketRegistry`). Цена записи: `priceCents / 10^priceDecimals`.

**`GET /api/oracle/records?fromSeq=&limit=`** — журнал записей для верификатора, тонкое чтение `oracle_records`:

```json
{"firstSeq":1,"records":[
 {"seq":1,"roundId":"1h-1790000180000","marketId":"BTC","asset":0,"ts":1790000001,"priceCents":8561201,
  "resultsHash":"0x…64 hex…","state":"unknown"},
 {"seq":2,"roundId":"T_OREC1-1h-1790000360000","marketId":"T_OREC1","asset":1,"ts":1790000002,
  "priceCents":8561202,"resultsHash":"0x…","state":"confirmed"}]}
```

- Строки по возрастанию `seq`, `seq >= fromSeq` (по умолчанию 0), не больше `limit` (по умолчанию 200, не больше
  1000 — большее значение режется до 1000; `limit` < 1, нечисло, `fromSeq` < 0 — `400`). Клиент листает по
  `последний seq + 1`, пока страница короче запрошенного `limit` — верификатор просит ровно 1000.
- `firstSeq` — наименьший `seq` этой базы независимо от `fromSeq`; `null` (при ответе `200`), пока записей нет.
  `seq` на цепи ниже него опубликованы до этой базы (верификатор проверяет их только по цепи, §7.2).
- В журнале **каждая** строка, и ушедшая в chainsvc, и ещё нет (держится по §8.2). `state` — то же, что показывает
  `oracleAnchor` на странице раунда: `unknown` (ещё не спрашивали или chainsvc не знает), `queued`, `in_flight`,
  `confirmed`, `conflict`. `roundId` — как в `GET /api/rounds/{roundId}/results.json`: `1h-<ms>` у BTC,
  `<рынок>-1h-<ms>` у остальных.
- Имена и типы полей сверены с чтением верификатора (`fetch_records_journal`, `load_registry`, `cross_check` в
  `tools/verify-oracle/verify_oracle.py`) прогоном настоящего JSON эндпоинтов через эти функции; правок в
  верификаторе не потребовалось.

### 8.5 Как проверить раунд не-BTC рынка вручную

Пусть стенд `$STAND`, а раунд — часовой раунд рынка `ETH`.

1. **Реестр.** `curl -s $STAND/api/markets/registry.json` → запись `ETH`: `index` (это `asset` на цепи) и
   `priceDecimals`.
2. **Запись.** `curl -s "$STAND/api/oracle/records?fromSeq=<seq>&limit=1"` (или листать журнал страницами по
   1000 и найти `roundId`) → `seq`, `asset`, `priceCents`, `resultsHash`, `marketId`. `asset` должен равняться
   `index` из п. 1, `marketId` — `ETH`.
3. **Итоги раунда.** `curl -s $STAND/api/rounds/<roundId>/results.json | shasum -a 256` — сумма должна равняться
   `resultsHash` без `0x` (скачанные байты хешируются как есть, без переформатирования); в документе
   `closePriceCents` равен `priceCents`, а корневой ключ `market` — `ETH` (у BTC этого ключа нет, байты
   документа остались прежними, `ResultsHasher`).
4. **Цена.** `priceCents / 10^priceDecimals` — цена закрытия раунда в единицах источника (для рынка шансов
   Polymarket — вероятность 0…1).
5. **Цепь.** `python3 tools/verify-oracle/verify_oracle.py <launcher id> --stand-url $STAND --from-seq <seq>` —
   для этого `seq` вывод покажет «asset N (ETH)», совпадение хеша, цены и актива. Руками: в спенде синглтона
   (`get_puzzle_and_solution` на coinset.org, §7) найти `CREATE_PUZZLE_ANNOUNCEMENT`; сообщение — CLVM-список
   `(seq ts priceCents resultsHash sourceFlag sourceTs asset)` из **семи** элементов, седьмой равен `asset` из п. 1;
   у BTC элементов шесть.

### 8.6 Запись, которую chainsvc уже держит (исправление по ходу)

`POST /v1/oracle/records` отвечает `acceptedSeqs` — только **вновь** принятые `seq`; уже известный в любом
состоянии chainsvc молча пропускает (`chain/c2-svc/src/oracle/queue.rs`, `chain_service.md` §10.7), тогда как
Javadoc сервера описывал обратное. Если ответ на POST терялся, когда chainsvc уже записал пачку на диск
(например, таймаут чтения клиента — `quarkus.rest-client.chainsvc.read-timeout=15000` в
`server/src/main/resources/application.properties`), сервер отправлял те же строки на каждом тике и вечно
получал пустой `acceptedSeqs`; а так как строка не становилась `chainsvc_queued`, её якорь никогда не сверялся и
оставался `unknown`, хотя запись была в цепи. Теперь про `seq` из пачки, которых нет в ответе, издатель спрашивает
`GET /v1/oracle/records/{seq}` и строки, которые chainsvc держит (`queued`, `in_flight`, `confirmed`,
`conflict`), помечает переданными вместе с его состоянием (`OracleRecordRepository.markKnown`). Вопросы идут по
возрастанию `seq` и кончаются на первой строке, которую chainsvc не держит (значит, сам POST отвергнут, и строки
за ней тоже); если chainsvc не отвечает даже на вопрос — проход заканчивается, а не ждёт таймаут на каждой пачке
из двадцати. Реконсиляция поллит по `seq`, содержимое не сравнивается — для этого пол `seq` (§8.3) и
верификатор.

### 8.7 Реконсиляция и другие рынки

`OracleReconciliationService` по `seq` не различает рынки; отличается повторная отправка записи, потерянной
chainsvc (`unknown` дольше 120 с после постановки): она теперь несёт тот же `asset`, что первая отправка, и не
уходит на chainsvc без формата 2 (иначе запись другого рынка стала бы ценой BTC). Тик — `concurrentExecution =
SKIP` (после простоя неподтверждённых строк много, а проход дольше минуты не должен догоняться вторым).
