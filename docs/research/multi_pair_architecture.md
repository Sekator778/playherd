# Архитектура N пар (мульти-ассет) — как Herd растёт с BTC на ETH/SOL/…

Дата: 2026-09-26. Все технические решения ниже — **предложение**, ни один пункт не пересматривает
зафиксированные Р-N; там, где предложение затрагивает то, что Р-N уже неявно зафиксировали для
одного актива (BTC), это явно отмечено как открытый вопрос в §11, а не решается этим документом.
Приоритет источников — как в `docs/INDEX.md`: при расхождении с `docs/product/decisions.md`
(Р-1…Р-59) верны решения; факты о живом коде — прямым чтением `engine/`/`server/`/`chain/`/`web/`
на 2026-09-26 (см. ссылки на файлы и строки по ходу); факты о Hyperliquid — прямым `POST
https://api.hyperliquid.xyz/info {"type":"meta"}`, сделанным для этого документа 2026-09-26
(§2), плюс уже существующие цитаты в `docs/research/hl_liquidation_math.md`.

## 0. Контекст запроса

Дословно, Р-59 (`docs/product/decisions.md`): «главный экран — лобби с плитками пар (сейчас BTC,
архитектура — на N пар); пара → "комната"... статистика, график толпы и рейтинги — отдельной
вкладкой». Это решение об **экране** (лобби/комната), реализация — зона `.claude/agents/game-designer.md`
и отдельного дизайн-исследования, уже запущенного тем же Р-59. Этот документ — **не про экраны**:
он про то, что должно измениться под экраном, чтобы вторая пара (пример Алекса — ETH, но ровно тот
же вопрос встаёт для любой) не требовала переписывать движок, сервер и оракул заново. Раздел про
веб (§9) фиксирует только маршрут/контракт, которым будущий экран лобби/комнаты будет пользоваться,
а не сам экран.

**Отличие от «Фазы 2» плана.** `docs/selection/final_top3.md` §2 фиксирует отдельную будущую фазу —
«общие рынки предсказаний на игрушечных деньгах поверх Action Layer (CHIP-50), не привязанные к
одному BTC up/down» (произвольные да/нет-рынки, любая тема). Это **не то же самое**, что предмет
этого документа: здесь речь о нескольких активах в **той же самой** механике «BTC up/down» (тот же
раунд, то же плечо x2–x40, тот же оракул-паттерн), просто активов Hyperliquid-perp несколько
(BTC, ETH, SOL, …), а не один. Ничего из СHIP-50/Action Layer этому документу не требуется.

## 2. Реальные данные Hyperliquid по BTC/ETH/SOL — живой фетч для этого документа

Источник: `POST https://api.hyperliquid.xyz/info {"type":"meta"}`, публичный `/info`-эндпоинт (тот
же, что уже используется проектом — `docs/research/hl_liquidation_math.md` §1.1/§4, `chain/c2-cli`,
`server/.../live/HyperliquidClient.java`), выполнено **2026-09-26** для этого документа, без ключей.

| Актив | `marginTableId` | Тиры (notional USDC → maxLeverage) | `szDecimals` |
|---|---|---|---|
| BTC | 56 | `[0, 150 000 000) → 40x`, `[150 000 000, ∞) → 20x` | **5** |
| ETH | 55 | `[0, 100 000 000) → 25x`, `[100 000 000, ∞) → 15x` | 4 |
| SOL | 54 | `[0, 70 000 000) → 20x`, `[70 000 000, ∞) → 10x` | 2 |

BTC-строка byte-в-byte совпадает с тем, что уже задокументировано в `hl_liquidation_math.md` §1.4/1.10
(`marginTableId=56`, тиры `[0,150M)→40x`/`[150M,∞)→20x`) — подтверждает, что живой формат `meta` не
менялся с 2026-09-25.

**Находка, отдельная от задачи мульти-ассета, но всплывшая при её проверке**: `PositionSizing.SIZE_SCALE
= 8` (`engine/.../PositionSizing.java:17`) обосновано в коде как «сатоши, стандартное деление BTC» —
но реальный `szDecimals` Hyperliquid для BTC равен **5**, не 8 (то есть Hyperliquid квантует размер
BTC-позиции до 0,00001 BTC, а не до 0,00000001). Это не баг сегодняшнего движка (округление до 8
знаков **точнее**, чем требует Hyperliquid, и для чистого paper-trading без реального ордера у
Hyperliquid лишняя точность безвредна — `PositionSizingPropertyTest` доказывает границу ошибки для
любого масштаба ≥ разумного), но если когда-нибудь размер позиции нужно будет передавать в реальный
Hyperliquid-ордер (`HyperliquidAdapter`, сейчас не реализован, `PLAN.md` §2), точность придётся
округлять вниз до фактического `szDecimals` актива — **иначе биржа отклонит ордер**. Для мульти-ассета
это значит: `SIZE_SCALE` должен стать функцией актива (§3.4), а не общей константой «8 = сатоши» —
для SOL, например, `szDecimals=2`, округление до 8 знаков было бы для него бессмысленно точным.

**Риск источника данных**: таблица выше — снимок на сегодня, не встроенная в код константа с
автообновлением (тот же способ, каким сейчас захардкожен `MarginTable.BTC` — см. §11 п.6). Hyperliquid
может менять `marginTableId`/тиры/`maxLeverage` без объявления; см. открытый вопрос в §11.

## 3. Движок (`engine/`) — измерение «актив»

Пакеты `margin`, `market`, `round` в `engine/` уже спроектированы как чистые, без побочных эффектов
(`docs/research/round_engine_design.md` §1) — это облегчает добавление параметра, но каждое из
следующих изменений аддитивно ломает текущие BTC-only сигнатуры, поэтому перечислено по одному.

### 3.1 `Asset` — новый маленький тип, `MarginTable` — реестр вместо константы

Предложение: `record Asset(String symbol)` или enum `Asset { BTC, ETH, SOL }` (открытый вопрос —
закрытый enum проще типобезопасно прокинуть через API/БД, но требует релиза кода на каждую новую
пару; открытая строка не требует релиза движка на новую пару, но теряет compile-time проверку —
решить в неделю реализации, не блокирует остальной дизайн).

`MarginTable.BTC` (константа) → `MarginTable.forAsset(Asset)` (реестр), заполненный **теми же**
значениями, что уже зафиксированы вручную для BTC (`hl_liquidation_math.md` §1.4) плюс новыми из §2
для ETH/SOL. Формула тиров (`maintenance_margin_rate`/`maintenance_deduction`,
`MarginTable.build(...)`, `MarginTier.java`) уже полностью общая по активу — она реализует
дословную формулу Hyperliquid, а не что-то специфичное для BTC; менять её не нужно, только вызывать
`build(...)` несколько раз вместо одного.

### 3.2 `Leverage.forNotional` — добавить параметр актива

`forNotional(int value, BigDecimal notional)` → `forNotional(int value, BigDecimal notional, Asset
asset)`, читает `MarginTable.forAsset(asset)` вместо жёстко зашитого `MarginTable.BTC`. `MIN=2` —
общий по докам Hyperliquid (2–3x минимум зависит от актива, но проект уже выбрал единый пол `2` для
всех — Р-12 фиксирует минимальную ставку, не минимальное плечо конкретного актива, так что `MIN=2`
как общий пол остаётся предложением без противоречия decisions.md); `MAX` становится
`MarginTable.forAsset(asset).tier(0).maxLeverage()` вместо жёстко `40`. Для BTC/ETH/SOL это будет
40/25/20 соответственно (§2) — то есть слайдер плеча (Р-33/Р-52 «разогревается к x40») должен
показывать **разный** потолок в зависимости от открытой пары — это продуктовое следствие для
game-designer, не для этого документа, но важно зафиксировать здесь как источник для него.

### 3.3 `LiquidationCalculator` — таблично-управляемая ставка вместо константы

`MAINTENANCE_MARGIN_RATE = MarginTable.BTC.tier(0).maintenanceMarginRate()` (константа класса) →
метод/параметр, берущий ставку из `MarginTable.forAsset(asset).tier(0)`. Сама формула ликвидации
(`liq_price = price - side * margin_available / position_size / (1 - l * side)`,
`hl_liquidation_math.md` §1.6) уже без всякого изменения общая для любого актива — Hyperliquid
формулирует её без привязки к BTC, наш класс просто выбрал константу вместо параметра, потому что
активов было ровно 0.999 (BTC). Golden vectors (`docs/research/hl_liquidation_math.md` §3) для BTC
не трогаются; для ETH/SOL нужен новый набор golden vectors, посчитанный тем же python/decimal
скриптом с новой ставкой tier0 (0.02 для ETH `1/(2*25)`, 0.025 для SOL `1/(2*20)`).

### 3.4 `PositionSizing.SIZE_SCALE` — по активу, из `szDecimals`

Предложение: не «8 знаков, потому что сатоши», а параметр `Asset.sizeScale()`, заполненный из
Hyperliquid `meta.universe[].szDecimals` (§2: BTC=5, ETH=4, SOL=2), с тем же обоснованием точности
(`PositionSizingPropertyTest`), но пересчитанным для меньшего масштаба — ошибка округления растёт
с уменьшением `sizeScale`, нужно заново доказать границу для SOL (`scale=2`) тем же property-тестом.

### 3.5 `RoundWindow`/`Round`/`Position` — актив в идентификаторе раунда

`RoundWindow.roundId()` **обязан** нести актив: сегодня `"1h-1790348400000"`, при двух активах в
одном и том же часовом окне без изменения получились бы два раунда с одинаковым `roundId` —
конфликт в `BetBook` (ключ по `roundId`), в `LedgerBook.reserveStake(player, roundId, ...)`, в
`oracle_records.round_id` (уникальный ключ, §5.6), в `player_round_history` (составной ключ
`(round_id, player_id)`, `V4__player_index.sql`). Предложение: `roundId() = asset.symbol() + "-" +
interval.code() + "-" + startMs` (например `"BTC-1h-1790348400000"`). Мёртвый `Round`-record уже
несёт нужное поле (`asset`, §1) — можно возродить его как реальный DTO раунда вместо изобретения
нового типа, либо просто добавить `Asset asset` в `RoundWindow` напрямую; выбор — деталь реализации,
не архитектурный вопрос.

**Совместимость истории**: если формат `roundId` меняется, все уже сыгранные BTC-раунды в
`round_results`/`player_round_history`/`oracle_records.round_id` останутся под **старым** форматом
(`"1h-<ms>"` без префикса актива) — переименовывать существующие строки не нужно и не стоит (первичные
ключи, ссылки из `oracleAnchor`, уже опубликованный `resultsHash` считает хеш от `canonical_json`,
который включает старый `round_id` буквально). Предложение: новый формат действует только для
раундов **новых** активов; BTC остаётся на старом (без префикса) до отдельного решения о полной
миграции — асимметрично, но не ломает ничего уже проверяемого публично (`verify-oracle`).

### 3.6 `GameEngine` — по (актив × серия), общий леджер

Сегодня один `GameEngine` на серию (2 инстанса: HOURLY, DAILY — `docs/research/round_engine_design.md`
§2). Конструктор уже принимает `LedgerBook`/`CrowdAccount` явно (`GameEngine(LedgerBook ledger,
CrowdAccount crowdAccount)`, `GameEngine.java:44-47`) — это готовый шов: предложение —
**один `GameEngine` на каждую пару `(asset, interval)`**, но все они делят **один и тот же**
`LedgerBook` (Р-6: баланс игрока — один на игру, не по паре), и каждый получает **свой**
`BetBook` (уже приватное поле инстанса, ничего менять не нужно) и **свой или общий**
`CrowdAccount` (открытый вопрос, §4.6). Для 3 активов × 2 серии — 6 инстансов `GameEngine`, один
`LedgerBook`, RoundScheduler дергает `runRound` на каждом независимо, когда его окно истекло.

**Р-13 «один игрок — один голос на раунд»** — сегодня это в точности означает «одна ставка на
`roundId`»; с раздельными `roundId` по активу (§3.5) это автоматически становится «одна ставка на
`(asset, interval, окно)»`, то есть игрок сможет одновременно держать позицию по BTC **и** по ETH в
одном и том же часе — технически бесплатно (никакого нового кода, просто следствие §3.5), но это
меняет смысл «голоса толпы» так, как Р-13 в момент принятия решения (когда актив был один) не имел
возможности предусмотреть. Вынесено как открытый вопрос (§11 п.2), не как решение этого документа.

## 4. Сервер (`server/`) — раунды, боты, цена, рейтинги, счёт толпы

### 4.1 Конфиг: список активов вместо одного

`GameConfig` (§1) получает `herd.assets` (предложение: список кодов, например `BTC,ETH,SOL`,
парсится так же, как `herd.mode`/`GameMode.parse`) вместо неявного единственного актива. Длительности
раундов (`herd.round-durations.*`) и тестовый режим (Р-46) — по факту **не специфичны для BTC**,
остаются общими для всех активов (то же часовое/суточное окно, тот же тестовый ускоренный режим) —
менять не нужно. `herd.bots.count` и `herd.execution.hyperliquid.asset-index` — см. §4.4 и §11 п.5
(про них отдельные вопросы, не автоматически «просто список»).

### 4.2 Цена — живая и replay

**Живая (`LivePriceSampler`, §1)**: сюрприз в свою пользу — запрос `metaAndAssetCtxs` уже возвращает
**весь** Hyperliquid-universe (все активы, все `markPx`) одним вызовом раз в 2 секунды
(`LivePriceSampler.java:47-53`). Расширение на N активов не требует ни одного лишнего HTTP-запроса —
только: (1) извлекать markPx не для одного индекса `"BTC"`, а для каждого сконфигурированного
актива по тому же паттерну поиска по `name` в `universe`; (2) держать N кольцевых буферов тиков
(`Deque<Tick>`) вместо одного `ticks`. Небольшое, изолированное изменение (S, §10).

**Replay (`PriceService.java:41`, `GameService.java:1399`)**: оба места читают жёстко `"/replay/btc_1m.csv"`
— заменить на путь, параметризованный активом (`"/replay/" + asset.symbol().toLowerCase() + "_1m.csv"`).
Сами файлы для новых активов — §6.

### 4.3 Планировщик и боты — цикл по (актив × серия)

`RoundSchedulerService.tick()` — `for (Interval interval : Interval.values())` (2 итерации) →
`for (Asset asset : config.assets()) for (Interval interval : Interval.values())` (2×N итераций).
Механика (`resolveOverdueRounds`, восстановление после рестарта через `RoundProgress`) не меняется
по существу — просто применяется на большее число независимых `(asset, interval)` пар. То же для
`RoundProgress.isSeeded(...)` — предложение: индексировать по `(asset, interval)`, а не только
`interval`.

`BotService` — `Map<Interval, ...>` → `Map<AssetInterval, ...>` (составной ключ или вложенная
`Map<Asset, Map<Interval, ...>>`). Открытый продуктовый вопрос (не инженерный) — те же самые 20
ботов (Р-46) ставят на **все** активы независимо (эффективно 20 ставок на раунд на каждую пару,
активность вырастет ×N без роста числа «личностей»-ботов), или бот-пул делится между активами
(каждый бот выбирает одну пару за раунд)? Первое — минимальное изменение кода (каждый бот просто
участвует в каждом (asset,interval) цикле независимо, как сегодня участвует в HOURLY и DAILY
одновременно); второе честнее выглядит как «живая площадка», но требует новой логики выбора пары
ботом. Вынесено в §11 п.5.

### 4.4 Рейтинги — что остаётся общим, что нужно решить

`RatingBook` считается из снимка `LedgerBook` (`round_engine_design.md`, `RatingBook.java:16-18`) —
баланс PLAY **уже** общий по всем активам (Р-6: один баланс на игру, не на рынок), поэтому
«**богачи**» (прирост баланса за сезон, Р-18) не меняются вообще: прирост баланса — это прирост
баланса независимо от того, на какой актив он получен. Никакого изменения не требуется — это
**предложение: без изменений**, с обоснованием ровно в этом абзаце.

«**Пророки**» (доля угаданных направлений, Р-18/Р-27) — per-round метрика; сегодня уже комбинирует
HOURLY и DAILY в одну `SeasonRecord` на игрока, и это уже помечено открытым вопросом самим
`round_engine_design.md` §5 п.1 («общий на игрока или отдельно по сериям?») — мульти-ассет добавляет
**тот же класс** вопроса на новом измерении: считать точность угадывания BTC и ETH вместе или
раздельно? Предложение по умолчанию (симметрично тому, как HOURLY+DAILY уже объединены) — считать
вместе, одна метрика «пророк» на игрока по всем активам и сериям; отдельная разбивка по активу — как
опция отображения на профиле игрока, не как новый тип рейтинга. Не решение — see §11 п.4.

### 4.5 «Счёт толпы» (`CrowdAccount`) — по активу или общий

Самый содержательный открытый вопрос всего документа. Сегодня: один процесс-инстанс, стартовый
капитал $100 000 (Р-17), **один непрерывный график с первого дня** (Р-25 — дословно: «капитал
"счёта толпы" не сбрасывается: один непрерывный график с первого дня»), с двумя линиями сравнения —
«просто держать BTC» и «анти-толпа» (Р-26). Каждая из этих трёх вещей плохо обобщается механически
на N активов:

- **Один общий `CrowdAccount`, который торгует то BTC, то ETH последовательно** (по тому, чей раунд
  сейчас разрешается) — сохраняет «один непрерывный график» Р-25 буквально, но линия сравнения
  «держать BTC» (Р-26) перестаёть быть осмысленной, если счёт то в BTC-позиции, то в ETH-позиции —
  сравнение «что было бы, если держать актив X» не имеет единственного X.
- **Отдельный `CrowdAccount` на каждый актив** (свои $100 000, свой график, своя линия «держать
  <актив>») — легко реализуется (конструктор уже параметризован стартовым капиталом,
  `CrowdAccount(BigDecimal startingCapital)`), естественно ложится на видение Р-59 «пара → комната
  → своя статистика/график толпы отдельной вкладкой» (то есть у каждой комнаты УЖЕ подразумевается
  свой блок статистики) — но формально **не совместим** с буквальным текстом Р-25 «один непрерывный
  график» для существующей BTC-истории, если это читать как «на весь продукт один график», а не «в
  рамках одной пары график непрерывен».

Предложение (не решение): каждой паре — свой `CrowdAccount` с собственным капиталом/графиком/линиями
сравнения (второй вариант), потому что он прямо соответствует уже принятому Р-59 «своя статистика
для комнаты» и не требует придумывать, что означает «держать BTC» для счёта, который сейчас торгует
ETH. Существующая BTC-история (Р-25 «с первого дня») интерпретируется как «continuity в рамках пары
BTC», не рвётся никак — просто остаётся тем, чем уже является. Общий межпарный агрегат («портфель
толпы по всем парам») можно добавить позже как отдельный, явно новый экран, не подменяющий Р-25.
**Требует подтверждения Алекса** — см. §11 п.3, поскольку затрагивает буквальную формулировку
зафиксированного решения.

### 4.6 Сезонный учёт — без изменений

Сезон (Р-10/Р-16, календарный месяц UTC) и вся бухгалтерия `LedgerBook`/`SeasonRecord` уже привязаны
к игроку, не к рынку/активу (§4.4) — стартовый пакет, инвариант консервации PLAY
(`round_engine_design.md` §3), вывод/ввод CAT — ничего из этого не знает о том, на каком активе
игрок играл. **Предложение: без изменений** — добавление активов не требует трогать `ledger`/`season`
пакеты вообще, кроме использования их существующего, уже актив-агностичного API из большего числа
`GameEngine`-инстансов (§3.6).

## 5. Оракул v2 — формат announcement и миграция

### 5.1 Что публикуется сегодня (напоминание с точными ссылками)

CLVM-список `(seq ts priceCents resultsHash sourceFlag sourceTs)`, `chain/c2-svc/src/oracle/types.rs:29-42`
(DTO), `spend.rs:11-13` (комментарий с точным порядком полей), подтверждено на живой цепи testnet11
`docs/research/oracle_verification.md` §5 (98 распознанных `seq`, 0 конфликтов, 0 разрывов,
2026-09-26). БД: `oracle_records` (`V2__oracle_reconciliation.sql`, дополнено `V3`/`V4`) хранит те же
6 полей плюс `round_id` (server-side, не идёт в announcement) — все под одним общим монотонным
`seq BIGINT PRIMARY KEY`, разделяемым **всеми** сериями (HOURLY и DAILY уже сегодня пишут в одну и ту
же последовательность `seq`, не в отдельные).

### 5.2 Прецедент эволюции формата уже пройден вживую

Самое первое announcement недели 1 (высота 4 735 705, до Р-41) использует **другой**, 3-элементный
формат `(priceCents, ts, seq)` — без `resultsHash`/`sourceFlag`/`sourceTs`, потому что Р-41 (хеш
итогов в ту же публикацию) был принят позже первого спенда. `verify_oracle.py` уже умеет с этим жить:
он не падает и не путает 3-элементные записи с 6-элементными, а откладывает их в отдельный список
«Unparsed announcement-shaped conditions» (`oracle_verification.md` §4, «Одно раннее announcement...
использует сверх-старый 3-элементный формат... инструмент честно показывает его отдельно... это
ожидаемая история эволюции формата, не находка»). Это прямое доказательство, что: (a) формат
announcement уже менялся один раз в этом проекте без переписывания истории, (b) публичный верификатор
уже спроектирован читать длину CLVM-списка как дискриминатор версии формата, а не падать на
неожиданной длине.

### 5.3 Предложение v2: добавить `asset` как седьмой элемент, в конец

`(seq ts priceCents resultsHash sourceFlag sourceTs asset)` — **новое поле в конце**, не в середине.
Обоснование: любой существующий код (включая уже опубликованные 98 записей на testnet11), который
позиционно распаковывает первые 6 элементов, продолжает работать без изменений на v2-записях —
вставка в середину сдвинула бы позиции `sourceFlag`/`sourceTs` и потребовала бы версионировать
**каждый** элемент кортежа, а не только читать длину. Сам `asset` — предложение: целочисленный
индекс в фиксированном реестре (`0=BTC, 1=ETH, 2=SOL, ...`), а не строка — короче в CLVM-байтах
(та же экономия, что уже сделана для `sourceFlag`: `0=live, 1=replay` вместо строки), и по аналогии
с уже существующим полем конфига `herd.execution.hyperliquid.asset-index`
(`GameConfig.java`, комментарий: «Hyperliquid assigns integer asset indices via its own /info
"meta" request») — только этот индекс наш собственный, маленький реестр (3-10 значений), а не
Hyperliquid-индекс (у Hyperliquid их 234, §2 «total assets: 234», незачем публиковать на цепь число
вроде «147» без контекста).

### 5.4 `seq` — один общий счётчик на все активы, не отдельные пространства

Предложение: **не** заводить отдельный `seq` на актив (`BTC-seq-1, BTC-seq-2, ETH-seq-1, ...`) —
оставить один глобальный монотонно растущий `seq`, как сегодня (уже общий между HOURLY и DAILY,
§5.1), и добавлять `asset` как отдельное поле записи. Это не меняет модель учёта, которую уже
реализует `verify_oracle.py` («первое появление, повторы, разрывы» — весь смысл понятия «разрыв в
последовательности `seq`» ломается, если `seq` не монотонен и не единственен) — раздельные
пространства `seq` по активу потребовали бы переписывать логику детектора «разрыва» с нуля на
что-то вроде «разрыв в подпоследовательности seq для актива X», что не даёт ничего, чего не даёт
уже работающая модель «один поток seq, каждый со своим полем asset».

### 5.5 Обновление `verify_oracle.py` и обратная совместимость

Ровно тот же паттерн, что уже реализован для 3-элементного формата (§5.2): декодер принимает длину
списка `∈ {3, 6, 7}`. Записи длины 6 (вся существующая история — 98 записей на 2026-09-26) при
чтении помечаются `asset=BTC` **неявно** (единственный актив, который вообще существовал, когда они
публиковались) — это не искажение истории, а буквальный факт: до появления второй пары всё, что
публиковалось, было BTC. Сверка со стендом (`--stand-url`, §1.2 инструмента) для старых записей
продолжает работать без изменений — раунды до появления второй пары как были привязаны к BTC-ценам,
так и остаются, просто теперь это явное поле, а не подразумеваемое по отсутствию альтернативы.
Публичный контракт инструмента («что проверяет» / «чего не проверяет», `oracle_verification.md` §1)
не меняется ни в одном пункте — только разбор одного дополнительного, седьмого элемента.

### 5.6 Миграция БД

Flyway `V6__oracle_multi_asset.sql` (предложение, имя следующее по номеру после `V5`):

```sql
ALTER TABLE oracle_records   ADD COLUMN asset TEXT NOT NULL DEFAULT 'BTC';
ALTER TABLE round_results    ADD COLUMN asset TEXT NOT NULL DEFAULT 'BTC';
ALTER TABLE player_round_history ADD COLUMN asset TEXT NOT NULL DEFAULT 'BTC';
```

`DEFAULT 'BTC'` на всех трёх — вся существующая история корректно размечается без бэкфилл-скрипта
(до этой миграции существовал ровно один актив). Составной первичный ключ `player_round_history
(round_id, player_id)` не обязан меняться, если §3.5 меняет `round_id` так, что он уже уникален по
активу (новый формат `"<asset>-<interval>-<startMs>"`) — колонка `asset` тут для удобства запросов
(«показать историю игрока только по ETH»), не для уникальности.

### 6.1 Реально измеренные числа (2026-09-25/26, testnet11, все ссылки уже в `docs/`)

### 6.2 Механика батчинга уже устроена так, что переносится на активы бесплатно

`build_oracle_publish_batch` (`spend.rs:57-82`) делает **один** `create_coin` (пересоздание
синглтона) и затем **один** `CREATE_PUZZLE_ANNOUNCEMENT` на каждую запись массива `&[OracleRecord]`
— массив уже сегодня смешивает записи **разных раундов** (HOURLY и DAILY закрываются на одной и той
же часовой границе, Р-40, и обе их записи уходят в один и тот же спенд). Ничто в этой функции не
знает и не проверяет, что все записи батча об одном и том же активе — она принимает произвольный
`&[OracleRecord]`. Это значит: расширение `OracleRecord` полем `asset` (§5.3) **автоматически**
даёт возможность publisher'у класть в один и тот же батч записи по BTC, ETH и SOL одновременно —
никакого нового on-chain примитива, только более длинный входной массив к уже существующему коду.

### 6.3 Два варианта — сравнение

**(a) Отдельный синглтон (launcher) на каждый актив.** N независимых `oracle-launch`, N независимых
очередей/publisher-инстансов chainsvc, N отдельных прогонов `verify_oracle.py --launcher-id <тот
или этот>` (инструмент и так уже принимает произвольный `launcher_id` любого синглтона, «не завязан
на этот конкретный проект», `oracle_verification.md` §3). На каждой часовой границе — N отдельных
спендов, каждый оплачивает полную фиксированную стоимость пересоздания синглтона (byte-cost
доминирует в измеренном бандле выше — 23 844 000 из 29 979 226, то есть ~80% cost'а бандла не
зависит от числа записей в нём). При N=3 это **утраивает** байт-стоимость и число отдельных
транзакций в мемпуле каждый час — при и без того документированной перегрузке мемпула testnet11
(`docs/research/week1_testnet_results.md` §5.1: 99.99% заполнения на день 1) лишние независимые
транзакции — прямой риск дороже проходить `get_fee_estimate`.

**(b) Один общий синглтон, батч на все активы в одном спенде** (то, что механика в §6.2 уже
позволяет). На каждой часовой границе — один спенд, несущий до 20 записей: сегодня 2 записи в час
(HOURLY+DAILY, один актив); при N=3 активах — 6 записей в час (3 актива × 2 серии). Фиксированная
byte-стоимость пересоздания синглтона оплачивается **один раз** за границу, а не N раз. Один
`verify_oracle.py`-прогон на единственный `launcher_id` продолжает проверять всю историю всех
активов сразу — не нужно помнить N разных launcher id при аудите.

### 6.4 Рекомендация и оговорка про запас батча

**Предложение: (b)**, потому что механика batching уже реализована и уже используется по ровно тому
же принципу («несколько ожидающих записей → один спенд»), и потому что Р-40 фиксирует «раз в час, на
границе часа», не «по синглтону на актив» — ничто в зафиксированном решении не требует раздельных
синглтонов. Единственная оговорка: `MAX_RECORDS_PER_SPEND = 20` был выбран (без явного обоснования
числа в источниках, кроме «task instruction») с запасом на **разовый** бэклог при 1 активе × 2
серии = 2 записи/час → 20 записей это ~10 часов backlog до упора в лимит при полном простое
publisher'а. При N=3 активах × 2 серии = 6 записей/час → тот же лимит даёт **~3.3 часа** запаса —
не блокер сегодня (инцидент §11/§12 `chain_service.md`, из-за которого backlog вообще накапливался,
уже исправлен startup-реконсиляцией), но при добавлении 4-й/5-й пары стоит пересчитать заново, а не
предполагать, что 20 записей — это «с запасом» навсегда.

- RPC-вызовы, сегодня неявно про единственный актив (`POST /api/rpc/rounds {"args":["HOURLY"]}` —
  используется и публичным верификатором, `oracle_verification.md` §2), получают второй аргумент:
  `{"args":["HOURLY","BTC"]}`. Обратная совместимость — предложение: без второго аргумента трактовать
  как `"BTC"` (текущее и на сегодня единственное поведение), чтобы не ломать уже написанный
  `verify_oracle.py`, пока он сам не обновлён под §5.5.
- Новая read-only ручка для лобби (game-designer'у, не в скоупе этого документа дальше перечисления):
  список активных пар с их метаданными (символ, текущий раунд каждой серии, максимальное плечо из
  §3.2) — по образцу того, как уже отдаётся `serverInfo()` (`ux_spec.md` §0, статус сервера).
- `/api/rounds/{id}/results.json` (FIXED INTERFACE 2, используется публичным верификатором) — теперь
  включает поле `asset` в `canonical_json` (влияет на `resultsHash`! см. предостережение в §5.6 —
  это осознанное решение при переходе на новые raundId/asset, не относится к уже опубликованным
  BTC-раундам, чей `canonical_json` заморожен и не пересчитывается).

## 9. Веб-роутинг: `/play/:asset`

Напоминание (§0): сами экраны — не эта работа. Но контракт под ними — да. `docs/product/ux_spec.md`
§1 прямо фиксирует «Предложение — ни один источник не фиксирует URL-схему» — то есть добавление
маршрута не требует пересмотра зафиксированного, только согласуется с уже принятым паттерном
(`/profile/:playerId`, тот же стиль параметра пути).

Предложение (по образцу существующих маршрутов `App.tsx`):

| Маршрут | Роль |
|---|---|
| `/play/:asset` | «Комната» пары (Р-59): открытый для ставок раунд именно этой пары, крупно вверх/вниз, таймер — экран, который сегодня частично покрывает `/round/:roundId`, но привязан к **текущему** раунду пары, а не к конкретному historical `roundId` |
| `/round/:roundId` | Не заменяется — постоянная ссылка на конкретный (в т.ч. прошлый) раунд остаётся, `roundId` теперь несёт актив в себе (§3.5), поэтому маршрут не меняется, только то, что в нём кодируется |
| `/crowd/:asset` (опция) или `/crowd` (если решение §4.5 — общий счёт) | Зависит от нерешённого §4.5 — этот документ не выбирает за Алекса |
| Лобби (`/` или новый `/play`) | Плитки пар — экран game-designer'а; этот документ фиксирует только то, что ему понадобится список активов из §8, не сам визуал |

## 11. Открытые вопросы Алексу

Компоновка вопросов, поднятых по ходу разделов 3–6 — сформулированы, не решены здесь; кандидаты для
переноса в `docs/product/decisions.md` → «Открытые вопросы» тем, кто с Алексом их обсуждает (не
этим документом — «READ-ONLY elsewhere», п. задания).

1. **Пространство `seq` оракула** (§5.4) — предложение: один общий монотонный `seq` на все активы
   (не отдельные пространства по активу). Нужно подтверждение, что это не противоречит какому-либо
   ещё не задокументированному ожиданию об «одном потоке seq на пару».
2. **Р-13 «один игрок — один голос на раунд»** (§3.6) — с раздельными `roundId` по активу игрок
   сможет одновременно держать позиции по BTC и ETH в одном и том же часе. Технически бесплатно,
   но меняет то, что Р-13 фактически означало в момент, когда актив был один. Подтвердить, что это
   желаемое поведение, а не случайное ослабление правила.
3. **`CrowdAccount` — по паре или общий** (§4.5) — самый весомый вопрос документа: свой $100 000/
   график/линии сравнения на каждую пару (предложение, совместимо с Р-59 «своя статистика для
   комнаты») против одного общего счёта, торгующего активы по очереди (буквально ближе к Р-25 «один
   непрерывный график», но ломает смысл линии сравнения «держать BTC», Р-26).
4. **«Пророки» — общий рейтинг по всем активам или раздельно по активу** (§4.4) — тот же класс
   вопроса, что уже открыт в `round_engine_design.md` §5 п.1 (HOURLY/DAILY общий или раздельный
   порог), теперь на измерении «актив». Предложение по умолчанию — общий (симметрично тому, как уже
   объединены HOURLY/DAILY).
5. **Боты на N активов** (§4.3) — те же 20 ботов ставят на каждую пару независимо (эффективно ×N
   активности без роста числа «личностей»), или пул делится между парами (каждый бот выбирает одну
   пару за раунд)?
6. **Источник правды для маржинальных таблиц по активу** (§2/§3.1) — сегодня `MarginTable.BTC`
   зашита вручную один раз (сверено с live API 2026-09-25) без механизма замечать, если Hyperliquid
   когда-нибудь изменит тиры/`maxLeverage`. При N активах тот же риск умножается на N. Стоит ли
   вводить периодическую сверку (например, при старте сервера или раз в сутки) конфигурации против
   живого `meta`, вместо чисто статичных констант — открыто, не решается этим документом.
7. **Кодировка `asset` в CLVM announcement** (§5.3) — целочисленный индекс в собственном маленьком
   реестре (предложение) против строкового символа. Затрагивает только байт-экономию и потребует
   опубликовать canonical-реестр (`0=BTC, 1=ETH, ...`) рядом с верификатором — тривиально, но
   нужно решить один раз до первой ETH-публикации, чтобы не менять формат снова сразу после запуска.
