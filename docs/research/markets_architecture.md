# Рынки, категории и живые цены — архитектура и фиксированные интерфейсы

Дата: 2026-10-01. Основание: Р-68…Р-71 (`the decision log`). Заменяет как рабочий план `docs/research/multi_pair_architecture.md` (тот остаётся источником обоснований; семь его вопросов §11 закрыты ниже техническими решениями Т-N). Факты об источниках данных — `docs/research/hl_multi_asset_live.md` и `docs/research/polymarket_data_api.md` (оба 2026-10-01, живые запросы). Референс навигации — `docs/product/design/polymarket-mobile-reference.md`.

Все пункты Т-N — технические решения сессия («предложение»): Алекс может пересмотреть любой, код построен так, чтобы выбор менялся конфигом или одной реализацией интерфейса.

## 1. Что строим

1. Лобби с панелями категорий → список пар → комната пары со ставкой с плечом (Р-69).
2. Все пары идут по живой цене источника; повтор истории остаётся только для тестов (Р-70).
3. Сверх уровня Polymarket (Р-71):

| Что | У Polymarket (2026-10-01, `polymarket-mobile-reference.md`) | В Herd |
|---|---|---|
| Плечо | только в разделе Perps, до 20x | на каждой паре любой категории: крипто до x40, акции/индексы/сырьё по лимиту Hyperliquid, шансы спорта и политики до x10 |
| Толпа | цена/шанс и объём | живой расклад UP/DOWN на карточке и в комнате, ставка «с толпой / против толпы» в одно касание, счёт толпы по каждой паре с результатом |
| Мои позиции | внутри раздела | одна полоса открытых ставок и позиций по всем парам с живым P&L |
| График | цена | цена + линии входа и ликвидации своей позиции и позиции толпы |
| Доверие к итогу | оракул UMA | цена и хеш итогов каждого раунда заякорены в Chia, отметка на итоге и публичный верификатор |
| Игра | — | короткие раунды с отсчётом, моменты итога, серии побед, сезоны и рейтинги |

## 2. Решения

| # | Решение |
|---|---|
| Т-1 | Категории: `crypto`, `politics`, `sports`, `stocks`, `indices`, `commodities`. Первые три названы Алексом (Р-69: спорт, политика, криптовалюта); порядок показа `crypto → politics → sports` — предложение (крипто первой: в ней исходная пара BTC и больше всего живых пар), меняется в одном месте — `Category.ORDER` на сервере и `CATEGORY_ORDER` в `web/src/api/marketMeta.ts`; остальные три — потому что у Hyperliquid есть такие перпы (`hl_multi_asset_live.md` §7), а у Polymarket Perps — такие же чипы. |
| Т-2 | Два вида рынков. `PERP` — цена актива в USD, с какой бы площадки она ни шла. С 2026-10-03 (§3.4) это спот Coinbase (запасная — Kraken) у BTC, ETH, SOL, XRP, DOGE и спот Hyperliquid (запасная — Coinbase) у HYPE; mark price перпов Hyperliquid dex `xyz` — у акций, индексов и сырья. `ODDS` — вероятность (0..1) одного исхода рынка Polymarket (CLOB midpoint). Механика одна: раунд, UP/DOWN, плечо, ликвидация по формуле Hyperliquid. |
| Т-3 | Лот-цена. Движок считает цены с 2 знаками (`Candle`, `LiquidationCalculator`). Сервер подаёт в движок цену лота: `engine = raw × 10^lotExp`, `lotExp = clamp(3 − floor(log10(raw)), 0, 8)` в момент листинга (для `ODDS` всегда 4), дальше не меняется. `priceDecimals = 2 + lotExp`. Наружу (API, график) идёт сырая цена с `priceDecimals` знаками. P&L и ликвидация от масштаба не зависят. |
| Т-4 | Плечо рынка: `PERP` — `min(40, maxLeverage)` из `meta` Hyperliquid (тир 0); `ODDS` — 10 (`herd.markets.odds.max-leverage`). Ставка поддерживающей маржи — `1/(2·maxLeverage)`. |
| Т-5 | Один баланс PLAY на игрока. Позиция — одна на игрока на раунд пары (Р-13 читается «на раунд пары»): в одном окне можно держать позиции по разным парам. |
| Т-6 | Счёт толпы — свой на каждую пару: $100 000, свой график, линии «держать актив» и «анти-толпа» (Р-17, Р-25, Р-26 в рамках пары). Сводка по всем парам — отдельным запросом. |
| Т-7 | Рейтинги и сезоны — общие по всем парам и сериям (как Р-30). |
| Т-8 | Боты: каждый бот в каждом раунде серии ставит на `herd.bots.markets-per-round` (3) случайных активных пар; плечо — в пределах лимита пары. |
| Т-9 | Оракул: один синглтон, один общий `seq`, запись на каждый раунд каждой пары. Актив — целочисленный индекс седьмым элементом announcement; для BTC (индекс 0) элемент опускается, история байт-в-байт прежняя. Реестр индексов публичен. |
| Т-10 | Список пар — конфиг плюс каталог Polymarket (топ по объёму за сутки с фильтрами). Параметры пары фиксируются при листинге и не меняются; изменилось у источника — новая пара. |
| Т-11 | Границы раундов для новой БД — кратные длительности «дневной» серии от эпохи Unix (в live: часовые на hh:00, дневные на 00:00 UTC; на стенде 3 и 15 минут — на :00, :03, … и :00, :15, …). Существующая БД сохраняет своё начало отсчёта. |
| Т-12 | Режимы: `replay` — прежний, только BTC, для тестов; `live` — рынки и цены из источников. `herd.prices.source = live \| synthetic`: `synthetic` — детерминированное случайное блуждание для CI, e2e и работы без сети. Стенд: `live`, раунды 180/900 с. |
| Т-13 | Совместимость: старая БД и журнал событий воспроизводятся без изменений — отсутствие рынка в событии означает BTC; `schema_version` событий не повышается; идентификаторы раундов и канонический JSON итогов BTC прежние. |

## 3. Модель

### 3.1 Рынок (сервер)

Интерфейсы — в коде, они и есть фиксированный контракт: `server/src/main/java/crowdvsmarket/server/markets/` — `Market` (запись: `id`, `kind`, `category`, `symbol`, `title`, `subtitle`, `iconUrl`, `source`, `sourceRef`, `sourceMeta`, `maxLeverage`, `lotExp`, `oracleIndex`, `status`, `listedAtMs`, `closedAtMs`, `closeReason`, `endsAtMs`; методы `spec()`, `priceDecimals()`, `toEngine`, `toRaw`, `rawString`, `lotExpFor`), `NewMarket`, `MarketKind`, `MarketStatus`, `Category`, `MarketRegistry` (`all`, `active`, `byId`, `require`, `categories`, `list`, `close`, `setListener`), `MarketListener` (`onListed`, `onClosed`).

BTC всегда есть в реестре: строку создаёт миграция `V7__markets.sql` (`id=BTC`, `lotExp=0`, `maxLeverage=40`, `oracleIndex=0`). Индекс оракула выдаёт реестр — следующий по порядку, никогда не переиспользуется.

### 3.2 Цены

Интерфейсы — `server/src/main/java/crowdvsmarket/server/prices/`: `MarketPrices` (`latest`, `series`, `resolve` — может ходить в сеть и никогда не вызывается под блокировкой движка, `soFar` — только память), `PricePoint`, `PriceQuote`, `RoundPriceData` (цены лота для `GameEngine.runRound`), `PriceUnavailableException`.

Правила (Т-9 цены, Р-23; второе ревью 2026-10-02 — F1…F7, L3; мост через дыру между живыми тиками — H1, H2):

1. **Тик** — (время получения ответа, сырая цена). Источник опрашивается по расписанию с `concurrentExecution = SKIP`: Hyperliquid основной dex — `metaAndAssetCtxs` раз в 3 с, поле `markPx`; dex `xyz` — тот же запрос с `"dex":"xyz"` раз в 6 с (вместе 600 из 1200 единиц лимита в минуту на IP, `hl_multi_asset_live.md` §5); Polymarket — один `POST https://clob.polymarket.com/midpoints` со всеми токенами раз в 3 с. **Только опрос — котировка.** Кроме ответов опроса в кольце лежат точки трёх других видов: история источника (`HISTORY`), копия цены живого тика через тихую дыру (`CARRIED`, п. 5) и **пин** границы рассчитанного раунда (`PIN`, п. 3). `latest()` (цена в лобби, боты, ставка) — последний *живой* тик: ни пин, ни копия, ни точка истории не сделают старую цену свежей; `series()` (график) — всё, кроме пинов. У копии и пина есть настоящий тик, чью цену они повторяют; его время — `sourceTs` итога (время «когда цену видели», а не когда её скопировали).
2. **Хранение.** Каждый опрос — одна строка `price_snapshots(source, at_ms, prices JSONB)`; в памяти — буфер тиков на рынок на `2 × длительность дневной серии + 10 мин`. При старте буфер восстанавливается из таблицы (живые тики). Строки старше окна удаляются раз в 10 минут. История, копии и пины — только в памяти и строк не пишут: после перезапуска возвращаются только живые тики.
3. **Цена на границе** `P(t)` — последний тик с `at ≤ t`, не старше `staleMs` (Hyperliquid 15 с, `xyz` 20 с, Polymarket 30 с). `open(N) = P(start)`, `close(N) = P(end)`; значит `close(N) = open(N+1)` (Р-40). Тик, свежий на границе, *и есть* цена на границе: история не сливается на `start` и раньше него, пока тик перед ним свеж; слияние только добавляет, ничего не заменяет. **Пин.** Рассчитанный раунд оставляет цены своих двух границ пином ровно в `start` и `end` — следующий раунд и раунд другой серии с общей границей (дневной расчёт идёт перед часовым при каждом проходе планировщика) читают ту же цену, а слияние истории для более длинного окна её не двигает. Пин не тик (п. 1). Кроме того, в этом процессе **ничего не сливается в кольцо на моменты `≤` последней границы, закреплённой пином для рынка** (`TickStore.latestPin`), и источник за этим отрезком не спрашивается: закреплённую цену не перепишет ни одно слияние, в каком бы порядке ни рассчитывались серии. Перезапуск забывает пины; открытие следующего раунда тогда берёт ядро из сохранённого закрытия предыдущего (Р-40). `sourceTs` итога — время последнего *настоящего* тика (живого или точки истории), откуда пришла цена закрытия; не пина и не копии.
4. **Путь раунда** — тики из `(start, end]`, свёрнутые не более чем в 30 свечей OHLC равной длины; первая свеча открывается ценой открытия, последняя закрывается ценой закрытия. Ликвидация проверяется по `low/high` свечей, как сейчас.
5. **Дыра.** Если между соседними тиками окна (включая границы) больше `maxGapMs` (Hyperliquid 30 с, Polymarket 90 с) — дыра добирается из истории источника, **что именно можно положить, зависит от того, чем история является** (`PriceSource.historyKind`):
   - *история — то же число, что тик* (Polymarket `data-api /v2/prices-history`, бакеты 60 с — мидпоинты стакана, как `/midpoints`; синтетический источник): добор в любую дыру. Бакет несёт «цена такая до следующей точки»: она продолжается копиями каждые 30 с до следующего бакета (не дальше 10 минут) и от последней точки до конца диапазона (не дальше бакета). Промежуток, **заканчивающийся терминальным тиком** (`resolution_seconds: 0`), заполняется, только если он не длиннее двух бакетов: отставание закрытых бакетов (200–330 с на живом краю, 81–82 с у закончившегося окна — `polymarket_data_api.md` §13.6) — не цена.
   - *история — цены сделок, тики — mark* (Hyperliquid `candleSnapshot` 1m; `hl_multi_asset_live.md` §3.4, §10 п. 5): свечи служат трём вещам и больше ничему. (1) **Прошлое первого опроса**: точки старше всех живых тиков рынка — по ним первый раунд нового рынка получает открытие, а комната — график. (2) **Мост через дыру между двумя живыми тиками** (следующий пункт списка). (3) **Свидетельство**: была ли сделка внутри дыры и какой была последняя сделка до неё (для правила тихого актива). Цена сделки не кладётся между живыми тиками ни в какой другой роли — иначе плоский mark рассчитывался как DOWN на закрытии сделки 27-минутной давности, а в путь попадал провал, по которому проверялась ликвидация. Свеча — только закрытая (`T < now`) и только со сделками (`n > 0`; заполнитель `n = 0` — повтор прошлого закрытия, не цена: `hl_multi_asset_live.md` §13.3); close даёт точку в `T`, low/high — две точки внутри минуты, open — только первая строка ответа. **Цена на границе раунда — close закрытой свечи перед ней** (на минутной границе это точка за 1 мс до неё), а не low/high свечи, внутри которой лежит граница; источник добавляет такую точку ровно в границу, когда последняя точка перед ней — не close.
   - **Мост** (`GapBridge`, `LiveMarketPrices.backfill`; H1, H2). Дыра, у которой оба соседа — *живые* тики (левый может быть пином или копией, за которыми стоит живой тик; левый край — начало окна, когда живой тик перед ним свеж на старте), закрывается свечами, которые её перекрывают, — целиком или никак. Условия: (а) **каждая минута** от минуты заполняемого участка до минуты правого живого тика имеет закрытую свечу со сделками: минута без сделок (заполнитель `n = 0`, строка, которой нет в ответе) или ещё не закрытая свеча правого тика оставляют дыру (повтор не чаще `backfillCooldownMs`); (б) **базис**: живая цена каждого из двух соседей лежит внутри [low, high] свечи *своей* минуты, расширенного на `herd.prices.hyperliquid.max-basis` (15 bp от живой цены по умолчанию); (в) от левого живого тика до правого не больше `herd.prices.hyperliquid.max-heal-ms` (30 минут по умолчанию). **Вклад свечи** — то, что нужно проверке ликвидации: её low и high (на трети и на двух третях минуты, low раньше, если свеча закрылась вверх) и close в конце минуты (`T = t + 59 999`). Точки соседних свечей не дальше 20,001 с одна от другой, поэтому полностью покрытая дыра выполняет правило «две соседние точки не дальше максимума 30 с», а пропущенная свеча даёт 80 с и ломает его; код проверяет и покрытие, и расстояния сам (при `max-gap` меньше 20,001 с мост ничего не закроет). Точка свечи на краю дыры берётся, только если попадает внутрь неё: остальное время той минуты видели живые тики. Мост закрывает дыру до правого живого тика целиком, в том числе за концом окна, — раунд, который начинается внутри дыры, дыры не найдёт; пины и всё слитое до последней закреплённой границы мост не трогает; цена на границе раунда — по правилу выше. При `max-heal-ms = 0` моста нет.
   - *Почему диапазон минуты, а не open/close соседней свечи, и почему 15 bp.* Замер 2026-10-02 по 7 476 меткам стенда: метка не дальше 5,16 bp от диапазона [low, high] своей минуты, а от одной точки той же минуты (open, close соседней свечи) — до 45 bp (95-й перцентиль 13 bp: шум минутного движения рынка, допуск 15 bp отверг бы 3,5–4,4% меток); `hl_multi_asset_live.md` §13.4. 15 bp — втрое больше максимума замера и около 12% наименьшей дистанции до ликвидации при 40x (`(1/40 − l)/(1 + l)` при `l = 1/80` — 1,23%).
   - *Почему потолок 30 минут* (**предложение**). Обе проверки смотрят только на концы дыры, и чем она длиннее, тем меньше они говорят о середине (метка и сделки могли разойтись и сойтись внутри) и тем больше минут раунда держится на ценах сделок, а не меток. 30 минут — половина часового раунда боевой конфигурации (одна дыра не кладёт на цены сделок больше половины раунда) и примерно тот отрезок, на котором измерялся базис (41 минута). Больший потолок — настройка `max-heal-ms`.
   - **Что перезапуск делает с идущими раундами теперь.** Сервер, не опрашивавший цены от секунд до 30 минут, рассчитывает идущие раунды ликвидных активов по свечам: дыра закрыта минутами со сделками, в путь раунда вошли low/high каждой минуты, ликвидация, которую подразумевает low свечи, находится; дыра через границу раундов не мешает раунду после неё (замер ликвидности — `hl_multi_asset_live.md` §13.5: за сутки ни одной минуты без сделок у BTC, ETH, SOL, HYPE, `xyz:XYZ100`; у `xyz:TSLA` целиком торговалось 60% 20-минутных окон, у DOGE 77%). Раунд остаётся дырой — повторяется и через час после конца отменяется с возвратом ставок (Р-23), как раньше, — если дыра длиннее 30 минут, в ней есть минута без сделок, метка соседа лежит вне диапазона своей минуты больше чем на допуск, или справа ещё нет живого тика (лента не вернулась). Не измерялось (**UNVERIFIED**): выходные и ночь у акций, резкие движения рынка (допуск мог бы отказать на них; отказ — это возврат ставок, а не расчёт по неверной цене).
   Нет цены на границе и после добора — `PriceUnavailableException`; планировщик повторяет попытку. **Р-79 (2026-10-06):** раунд без цены возвращает ставки через N минут после конца, но не раньше чем через N минут после старта сервера или его паузы (перезапуск, первый проход планировщика, перерыв между проходами больше 15 с — сон Mac), — 5 минут у Hyperliquid, Coinbase, Kraken и спота Hyperliquid, 15 у Polymarket, 2 при живой второй бирже (Р-77, §3.4); раунд без ставок, которому нет цены, пропускается сразу; любой другой сбой, как и прежде, отменяет раунд через час после конца окна (Р-23), час — и верхняя граница для всех. Разбор — `docs/research/series_blocking.md`. История запрашивается не чаще раза в `backfillCooldownMs` (60 с) на рынок.
   **Тихий актив** (акция вне часов биржи, неходовая монета): у дыры может не быть ничего, потому что ничего не торговалось. Тогда цена **последнего живого тика** (mark, не close свечи) продолжается копиями (`CARRIED`) каждые 10 с, если выполнено всё: источник ответил; внутри дыры у него нет точек (у источника с ценами сделок — ни одной сделки); дыра не длиннее `herd.prices.quiet-carry-max-ms` (10 минут — **предложение**: перезапуск и короткий сбой, не час тишины); справа живой тик с той же ценой — а если справа тика ещё нет (хвост окна, лента не вернулась), последняя сделка источника равна цене левого тика; и (для источника с ценами сделок) левый тик живой — копия живого тика ещё живая, точка истории — нет. Иначе дыра остаётся: раунд ждёт и в конце концов отменяется, а не рассчитывается на выдуманной плоской линии. Дыра, в которой актив торговался, тихой не считается — её закрывает только мост (выше), или она остаётся.
6. **Синтетический источник** — случайное блуждание с фиксированным зерном на рынок, тик раз в секунду; в тестах тики можно подать вручную.
7. В режиме `replay` всё это не участвует: цены BTC идут из `ReplayRoundPrices`, как раньше.
8. **Засев истории** (`HistorySeeder`). Рынок получает недавнее прошлое сразу после листинга и по опросу ленты — если ни одного тика свежего на начало идущего окна (`RunningWindows`: дневного и часового) нет, не только при пустом кольце (рестарт через начало раунда оставляет «устаревшие» тики и раунд без цены открытия). Объём — `max(15 мин, DAILY)`, не больше суток; источник «той же цены» заполняет дыры кольца, источник «цен сделок» — только прошлое первого живого тика, и его не спрашивают, если живой тик лежит на `start` или раньше (история туда не лягла бы). Источник Hyperliquid засевается **только закрытыми свечами** (свеча в процессе даёт `h` как свежую цену). Каждая пара (рынок, начала идущих окон) пробуется один раз; неудавшаяся попытка, или попытка, после которой цены на начало всё ещё нет (у источника пока нет данных), повторяется через 1, 2, 4… минут, но интервал не растёт выше 15 минут. **Старт растянут по бюджету Hyperliquid** (1200 в минуту на IP; опрос 600 + каталог 40): засев одного рынка — `candleSnapshot`, вес 20 + 1 на 60 строк (округление **UNVERIFIED**, считаем вверх) и 30 минут просмотра назад — 21 на стенде и 45 при суточном `DAILY`; 12 рынков разом стоили бы 252 (стенд, 892 из 1200) и 540 (прод, 1180 из 1200). Засевы идут по одному в `60 с / ⌊бюджет / вес⌋` (`herd.prices.hyperliquid.seed-budget-per-minute`, 260 = 900 − 640): раз в 5 с на стенде (в первую минуту 252, итого 892) и раз в 12 с в проде (пять в первую минуту, 225, итого 865). Очереди разных источников независимы.
9. **Границы раундов в live.** История Hyperliquid — минутная, цена на границе точна только на целой минуте. Сервер с живыми источниками (`herd.mode=live`, `herd.prices.source=live`, планировщик включён) **не стартует**, если начало отсчёта календаря или любая из двух длительностей раундов не кратны 60 с (`RoundAlignmentCheck`; свежая БД в live выравнивает начало сама — Т-11, БД из режима `replay` хранит миллисекунду первого запуска). `herd.prices.require-minute-aligned-rounds=false` заменяет отказ строкой ERROR в журнале.

### 3.3 Каталог

- `PERP`: при старте для каждого имени из `herd.markets.crypto|stocks|indices|commodities`, которого нет в реестре, берётся `meta` источника: `maxLeverage`, `szDecimals`, `marginTableId`, текущая цена → `lotExp`; делистнутые (`isDelisted`) пропускаются. Источник недоступен при первом старте — рынок листится при следующей успешной попытке (раз в минуту). **Закрытие при делистинге** (`HyperliquidCatalog.watch`, раз в 5 с из памяти): рынок актива, который источник пометил `isDelisted`, закрывается, когда **не меньше трёх успешных ответов опроса подряд** говорят «делистнут», первый из них был не меньше 10 с назад, а последний не старше 15 с; ответ с живым активом или неудавшийся опрос начинает счёт заново. Причина — «The asset was delisted at the source». Один ответ и дальше только сбои не закрывают рынок навсегда; BTC не закрывается никогда (строка миграции V7).
- `ODDS` (`herd.markets.polymarket.enabled`): раз в 5 минут `GET gamma-api /markets/keyset?tag_id=<2|1>&closed=false&order=volume24hr&ascending=false&limit=50`; кандидаты — `acceptingOrders`, `enableOrderBook`, два исхода, конец не раньше чем через 30 минут; затем живой `midpoint` и `spread` из CLOB: `0.10 ≤ mid ≤ 0.90`, спред ≤ 0.05. Берётся исход с индексом 0. Держим `herd.markets.politics.count` (3) и `herd.markets.sports.count` (3) активных; для спорта сначала идущие матчи (`events/keyset?tag_id=1&live=true`). Одно событие (игра) — не больше одного рынка. **Спорт — только «кто победит» (S1).** Кандидат спорта — рынок с `sportsMarketType == "moneyline"` (победитель игры; `child_moneyline` — одна карта или сет серии, `first_half_moneyline`, `q1_moneyline` — период, `totals`, `spreads`, `team_totals`, `nrfi` и ещё сотни типов — не кандидаты: у матча MLB 31 рынок восьми типов в одном событии, `polymarket_data_api.md` §13.7); рынок спорта без этого поля (фьючерс лиги) — не кандидат; у политики поля нет и оно не требуется. **Остывание игры:** после того как каталог закрыл любой рынок игры (`gameId`, любая причина), ни один рынок этой игры не листится `herd.markets.polymarket.game-cooldown` (6 часов по умолчанию; 0 выключает) — иначе, как видели вживую 2026-10-01, закрытый на 97% рынок победителя «Phillies — Braves» заменялся тоталом «O/U 8.5» той же игры под тем же тикером `PHI`. Остывание читается из реестра (`closedAtMs` закрытого рынка и `gameId` в его `sourceMeta`), поэтому переживает перезапуск; на политику и на игру без `gameId` оно не распространяется. Рынков меньше заданного числа — нормально: категория добирается, когда появляется следующая игра. Каждый листнутый рынок передаётся в засев истории (п. 8 §3.2).
- **Подпись карточки** (`MarketLabels`; источники — `polymarket_data_api.md` §13.5, измерено 2026-10-02). *Тикер* — до 8 знаков, верхний регистр, **уникальный среди активных рынков любой категории** (закрытый свой тикер отдаёт): первый свободный из списка кандидатов, затем число (`PHI`, `PHI2`). Игра: `DRAW` для рынка на ничью, иначе аббревиатура команды, когда её даёт Gamma (`teams[].abbreviation` — только в `events/keyset` для идущих игр), иначе название команды, сокращённое до 8 знаков (короткое — целиком, длинное — по последнему слову: `PHILLIES`, иначе начало). Человек или предмет: последнее слово с заглавной буквы имени — имя берётся из собственной подписи рынка `groupItemTitle` («Luiz Inácio Lula da Silva» → `SILVA`), если вопрос её содержит, иначе из первого имени в вопросе («Will Elon Musk post …» → `MUSK`). Дальше — другие слова имени и вопроса: так разрешается совпадение («следующее отличительное слово»). **Общие слова тикером не бывают**: страна в любой записи (`US`, `U.S.`, `USA`), служебные и вопросительные слова (Will, The, A, Who, Which, Before, After, By …), месяцы, числа и годы, однобуквенные слова; голое Yes/No/Over/Under — тоже ничего не называет. *Подзаголовок* — что за исход у карточки: игра — «`<исход> to win · <лига или турнир>`» (лига — серия события, `series[0].title`, иначе `sport.name`; ничья — «Draw»; тоталы и форы подпись умеет — исход и лига, — но после S1 каталог их не листит), остальное — «`<исход> · <название события>`», название — только если оно не повторяет вопрос.
- **Закрытие `ODDS`** (причины — простые предложения, они показываются игрокам как есть): *«The source market ended»* — рынок закрыт у источника, проверка Gamma раз в обновление **двумя запросами на пачку токенов**: поиск по `clob_token_ids` без `closed` и с `closed=false` закрытых не отдаёт — только с `closed=true` (`polymarket_data_api.md` §13.1), поэтому открытые читаются с `closed=false` (их `oneDayPriceChange`), закрытые — с `closed=true`; *«The source market stopped trading»* — токен пропал из ответа `/midpoints` на 60 с **в не меньше чем трёх успешных ответах подряд, последний не старше 15 с**; неудавшийся опрос, ответ без всех токенов (сбой CLOB, не закрытие всех рынков сразу) и ответ с токеном начинают счёт заново — один частичный ответ и таймаут CLOB закрыть рынок навсегда не могут; *«Price left the 3%–97% range»* — `mid` вышел из `[0.03, 0.97]`; *«The source market ends in less than 5 minutes»* — до конца меньше 5 минут (у игры конца нет: `endDate` — начало матча). Закрытый рынок не открывает новых раундов, закрытый id заново не листится; раунд в окне ставок и идущий раунд отменяются с возвратом ставок (причина «market closed»). Три последних правила проверяются раз в 5 с из памяти и просят ранний долив категории.

### 3.4 Крипта с первоисточников: основная и запасная биржа (Р-74…Р-76, 2026-10-03)

Первая итерация перевода на первоисточники (`docs/research/primary_sources.md` §4, Р-74). Код — `server/src/main/java/crowdvsmarket/server/prices/` (`CoinbasePriceSource`, `KrakenPriceSource`, `HyperliquidSpotPriceSource`, `StreamSupervisor`, `JdkWebSocketTransport`, `CandleHistory`, `Instruments`, `RoundVenues`) и `markets/catalog/SpotCatalog`. В комментариях этих классов — замеры с датами.

**1. Рынки.**

| Рынки | Основная биржа | Запасная |
|---|---|---|
| `spot_BTC`, `spot_ETH`, `spot_SOL`, `spot_XRP`, `spot_DOGE` | Coinbase Exchange: продукты `BTC-USD` … | Kraken: пары `BTC/USD` … |
| `spot_HYPE` | спот Hyperliquid, пара HYPE/USDC | Coinbase, продукт `HYPE-USD` |

- Пара Hyperliquid — имя `@<index>` из `spotMeta`; находится по именам токенов, не зашита в код.
- `Market.source`/`sourceRef` — основная биржа; запасная записана при листинге в `sourceMeta.backup {source, ref}` и дальше не меняется (Т-10).
- Kraken-пара перед записью сверяется с `/0/public/AssetPairs`; если Kraken её не знает, рынок листится без запасной.
- Плечо — `herd.markets.spot.max-leverage` (прежние потолки: 40/25/20/20/10/10).
- `lotExp` — по первой цене основной биржи.
- **Замена (Т-10).** Перед листингом `SpotCatalog` закрывает активный рынок той же категории и символа с другим источником. Причина видна игрокам как есть: «Moved to a new price source: Coinbase» или «Moved to a new price source: Hyperliquid spot».
  - Закрытие отменяет идущие раунды с возвратом ставок.
  - Новый рынок листится только после успешного закрытия.
  - BTC закрывается только этим путём; делистинг его не закрывает.
  - На стенде 2026-10-03 в 16:18 UTC закрыты BTC, ETH, SOL, XRP, DOGE, HYPE: отменено 24 раунда, возвращено 41 ставка. Новые рынки получили индексы оракула 55–60.

**2. Живые цены — по WebSocket (Р-76).**
- Площадки и каналы:
  - Coinbase `wss://ws-feed.exchange.coinbase.com` — каналы `ticker` и `heartbeat`;
  - Kraken `wss://ws.kraken.com/v2` — `ticker` с `event_trigger=bbo`, потому что по сделкам он слишком редкий;
  - Hyperliquid `wss://api.hyperliquid.xyz/ws` — `allMids`.
- Соединения держит JDK `java.net.http.WebSocket`, обратные вызовы идут на виртуальных потоках.
- `StreamSupervisor` переподключает соединение через 1, 2, 4… с, до 60 с. Отсрочка сбрасывается только после данных подписанного канала или 30 с жизни соединения; после короткой сессии — пауза не меньше 5 с.
- Опрос из памяти идёт раз в 2 с; фиды `coinbase`, `kraken`, `hyperliquid:spot`.
- Котировка старше `fresh-ms` (Coinbase и Kraken 5 с, Hyperliquid spot 8 с) заменяется одним REST-запросом той же биржи:
  - Coinbase — `/products/{id}/ticker`;
  - Kraken — `/0/public/Ticker`, несколько пар за раз; если Kraken не знает одну из пар, запрос повторяется по одной паре;
  - Hyperliquid — `spotMetaAndAssetCtxs`, поле `midPx`.
- Тик = (bid + ask) / 2; у спота Hyperliquid — значение `allMids`.

**Замеры 2026-10-03 из Германии.**
- Частота сообщений:
  - Coinbase `ticker` — 172 в минуту у BTC-USD и 6 в минуту у DOGE-USD (тишина до 53 с), heartbeat раз в секунду;
  - Kraken `bbo` — средний промежуток 0,27–0,58 с, самый длинный 7,4–23,1 с;
  - `allMids` — раз в 5,0 с.
- Мидпоинт против диапазона своей минутной свечи: Coinbase — не дальше 1,62 б.п. (99-й перцентиль 0,42), Kraken — не дальше 4,19 б.п. (99-й перцентиль 2,84). Отсюда `max-basis` 15 б.п. у каждой площадки.
- Мидпоинт Kraken против Coinbase: в среднем 0,36–1,24 б.п. по парам, максимум 5,03 б.п. (DOGE).

**3. История** — минутные свечи сделок, `HistoryKind.TRADE_PRICES`; правила §3.2 п. 5 и п. 8 те же.
- Coinbase — `/products/{id}/candles`, не больше 300 за запрос.
- Kraken — `/0/public/OHLC`. Отдаёт только последние 720 строк, около 12 часов, при любом `since` (замер 2026-10-03). Всё старше — «нет данных»: мост через более старую дыру не строится, засев довольствуется тем, что есть.
- Hyperliquid — `candleSnapshot` по `@<index>`.

**4. Раунд целиком на одной бирже (Р-76).**
- **Отдельное кольцо тиков на каждую площадку.** Ключ запасной — `<marketId>~<источник>` (например `spot_BTC~kraken`), в `TickStore` и в `price_snapshots`; при старте восстанавливается как любой тик. Теневые рынки не попадают в реестр, движок, API и реестр оракула.
- **Выбор биржи** делается один раз — на ближайшем такте планировщика после начала окна, по состоянию колец на момент начала:
  1. живой тик, свежий на начале (`staleMs` 15 с): сначала основная, потом запасная. Пин и перенос считаются тем живым тиком, за которым стоят;
  2. иначе прочие свидетельства — история, перенос, пин: сначала основная;
  3. иначе решение откладывается до расчёта, и при лечении основная снова первой.
- Выбор записывается в `round_venues` (миграция V9) один раз и читается обратно.
- Раунд считается только по кольцу своей биржи: открытие, закрытие, путь, ликвидация. Если его биржа не даёт цены — ожидание, лечение свечами до 30 минут и возврат по Р-77/Р-79 (через 2 минуты при живой второй бирже, иначе через 5 минут; не раньше чем через столько же после старта или паузы сервера; час — верхняя граница, Р-23). На другую биржу раунд не переключается.
- На стыке смены биржи открытие следующего раунда может отличаться от закрытия предыдущего на базис бирж (замер выше). Р-40 действует внутри одной биржи.
- **Проверено на стенде 2026-10-03.** Coinbase выключали с 16:38 до 16:47 UTC (`herd.prices.disabled-venues=coinbase`):
  - раунды BTC, ETH, SOL, XRP, начавшиеся в 16:39 и 16:45, рассчитаны по Kraken;
  - раунд, начатый на Coinbase в 16:36, после возвращения Coinbase закрыт его свечами;
  - у DOGE дыра не закрылась: в минуте правого живого тика не было свечи со сделками, и раунд ждёт.
- **Пока раунд ждёт свою биржу, серия рынка стоит.** Следующий раунд не открывается, потому что раунды серии рассчитываются по порядку; окна, на которые за это время не открывались ставки, пропускаются (на стенде пропущено окно 16:42–16:45). Разбор — `docs/research/series_blocking.md`.
- **Р-77: раунд держит серию не дольше 2 минут.** Если через `herd.prices.venue-release-after-ms` (120 000 мс) после конца раунда — а после старта или паузы сервера не раньше чем через столько же после неё (Р-79) — его биржа всё ещё не даёт цены, а другая биржа рынка жива (её живой тик не старше `staleMs`), раунд возвращает ставки с причиной «The exchange of this round stopped sending prices; stakes returned»; биржа остаётся записанной в `round_results`. Серия идёт дальше, а биржа следующего раунда выбирается обычным правилом. Если молчат обе биржи — правило Р-79 с N биржи раунда (5 минут). Отсчёт и здесь не раньше старта или паузы сервера (Р-79). Проверено на стенде 2026-10-03 в 19:43–19:48 UTC: возврат ровно через 2 минуты, следующие раунды рассчитаны по Kraken.

**5. Что раунд сообщает о себе.**
- Биржа раунда записывается в `round_results.venue`, в событие `RoundResolved` и в канонический JSON — корневым ключом `"venue"`. Ключ есть только у рынков с биржами; у BTC и прежних форм его нет, байты прежние (Т-13).
- Журнал записей оракула (`/api/oracle/records`) показывает биржу каждой записи; `registry.json` — `backup {source, ref}` у рынка.
- Запись на цепи прежняя: биржа входит в неё только через `resultsHash`.
- `tools/verify-oracle` сверяет биржу журнала и документа и проверяет, что это основная или запасная из реестра. Прогон 2026-10-03: 7520 раундов совпали по хешу, цене, активу и бирже.

**6. Показ.**
- `latest` — основная, пока свежа, иначе запасная; источник цены — в `MarketPriceDto.venue`.
- График — только серия основной биржи; пока она молчит, на графике разрыв и подпись.
- `MarketDto.backupSource` — запасная биржа рынка; `RoundBase.source` — биржа раунда.
- Состояние потоков (connected, silent, rest-fallback, disabled) — в операторском `GET /api/admin/status`, поле `priceFeeds`. Публичная страница статуса показывает источники по рынкам.

**7. Выключатель** `herd.prices.disabled-venues` (например `coinbase`): площадка не даёт цены вовсе — ни потока, ни REST. Нужен, чтобы проверить запасную биржу на стенде.

**8. Не сделано (UNVERIFIED или на потом).**
- Канал `ticker` Coinbase идёт только по сделкам, поэтому тихую пару (DOGE) почти каждый опрос читает REST.
- У Kraken нет времени последней сделки, поэтому тихая дыра в конце окна остаётся дырой.
- `HYPE-USD` при листинге не сверяется.

## 4. Раунды

1. Ключ серии — `(marketId, Interval)`. `RoundProgress`, `EngineHub`, боты, планировщик работают по этому ключу. Движки одного рынка делят его `CrowdAccount`; все движки делят один `LedgerBook`.
2. Новый рынок получает как идущее окно то, в котором находится «сейчас» (а не первое окно календаря).
3. **Расчёт атомарен.** Цена берётся до блокировки (`MarketPrices.resolve`). Под блокировкой на запись: повторная проверка `round_results` (раунд уже рассчитан — выход), затем одна транзакция БД: событие `RoundResolved`, строка `round_results`, строки `player_round_history`, запись оракула; применение события к движку — внутри той же транзакции. Ошибка — транзакция откатывается и состояние в памяти пересобирается из журнала (`EngineRebuildService.rebuild()`). То же для отмены.
4. Тик планировщика — `concurrentExecution = SKIP`.
5. **Догон после простоя.** Окно со ставками всегда рассчитывается или отменяется. Пустое окно, просроченное больше чем на одну длительность, не рассчитывается: указатель серии переводится на окно, содержащее «сейчас», без события, итога и записи оракула.
6. `placeBet` отклоняет раунд, который уже есть в `round_results` (отменён оператором), рынок не `ACTIVE`, плечо выше лимита рынка.
7. Путь в событии `RoundResolved` — не больше 30 свечей; для раунда без ставок — одна свеча (open → close).
8. **Указатель серии не стоит позади ставки.** При пересборке и при выдаче серии рынку указатель стоит не позже самого раннего окна, где ещё лежит ставка и нет итога (`SeriesSeeder`); иначе после остановки через конец окна ставок ставка не рассчиталась бы и не вернулась никогда. Рынку, закрытому в БД, пересборка возвращает ставки во всех таких окнах (не только вокруг момента закрытия). Источник: `server/.../service/SeriesSeeder.java`, `scheduler/EngineStateBuilder.java`.
9. **Пересборка строит состояние рядом и подменяет его целиком.** Свежие `EngineHub` и лента ставок, воспроизведение журнала, указатели серий — всё готово, и только тогда подмена; при сбое остаётся прежнее состояние, а полусобранный хаб запросам недоступен. Источник: `scheduler/EngineRebuildService.java`, `EngineStateBuilder.java`.
10. **Сбой пересборки после неудачного расчёта — fail-stop.** Если пересборка по п.3 тоже не удалась, память может опережать БД: `EngineRebuildService.isReady()` = `false`, пока пересборка не удастся. Всё, что меняет состояние (ставки, вход, ник, вывод, зачёт ввода, расчёт, отмена, действия оператора), и все чтения из движка (баланс и «в игре», журнал, рейтинги, счёт толпы, раунды пары, лента ставок, профиль, `home`) отвечают 503 `ENGINE_NOT_READY`; чтения из БД и без движка (итог рассчитанного или отменённого раунда, журнал отмен, непросмотренные итоги, статус вывода и ввода, цены, превью ликвидации, `serverInfo`) отвечают как обычно. Планировщик повторяет пересборку не чаще раза в `herd.rebuild.retry-ms` (2 с), пока она не удастся; закрытие и листинг рынка в это время не бросают исключение и подхватываются пересборкой. Источник: javadoc `EngineRebuildService`.
11. **Любой сбой расчёта — неудачная попытка.** Источник цен упал (любое исключение, не только `PriceUnavailableException`), цены нельзя взять (открытие или закрытие не положительны после округления до двух знаков; путь длиннее 30 свечей в `live` — проверяется до блокировки), транзакция расчёта не прошла: попытка повторяется с отсрочкой (п.13), через час после конца окна раунд отменяется с возвратом (Р-23). **Шлюз `OracleSeqGate` (§7 п.4) спрашивают вокруг самого расчёта и больше нигде:** `seq` резервирует только расчёт. Пока `open()` = `false`, ни один раунд не рассчитывается, а всё, что `seq` не резервирует, идёт как обычно — скачок серии через пустые окна (без события, итога и записи оракула), выдача серии рынку без указателя, боты, публикация очереди, возврат ставок раунда, которому час (событие и строка итога, записи оракула нет; причина та же, что у любого несостоявшегося расчёта: «settlement failed within 1 hour of round close»). Раз в минуту об этом пишется в журнал. Остаток, известный и не закрытый: окно, закончившееся не больше шага назад, пустым-пропускаемым не считается (оно рассчитывается и пишет запись оракула), поэтому при закрытом шлюзе указатель серии стоит на нём — на окно позади часов — и приём ставок в серии закрыт, пока шлюз не откроется. Источник: `scheduler/RoundSchedulerService.java`, `service/RoundPriceChecks.java`, `chain/OracleSeqGate.java`, тесты `OracleGateSchedulerTest`, `SettlementFailureRefundTest`; ревью ядра 2026-10-02, находка 5.
12. **Указатель серии не стоит впереди часов.** Начало серии — более раннее из двух: окно после последней строки `round_results` серии и окно, содержащее «сейчас» (после остановки указатель по-прежнему догоняет от последней строки), а затем не позже самого раннего окна со ставкой без итога (п.8). Раньше строка итога окна, которое ещё не началось (оператор отменил раунд ставок или идущий раунд при ставке на следующий), ставила указатель после него, и перезапуск внутри того же окна показывал идущий раунд, который не начался, и принимал ставки на раунд через два окна. Источник: `service/SeriesSeeder.java`, тест `SeriesCursorNeverAheadOfTheClockTest`; ревью ядра, находка 4.
13. **Повтор расчёта с отсрочкой; пересборка только если память могла измениться.** После k-й неудачной попытки окна следующая — не раньше чем через `min(60 с, 2^k с)` (2, 4, 8 … 60 с); состояние хранится по серии для окна, на которое указывает указатель (`scheduler/SettlementBackoff.java`); возврат ставок через час после конца окна отсрочкой не задерживается, первая его попытка делается сразу. Сбой расчёта запускает пересборку движка из журнала (п.3, п.10) только если он случился после записи события и применения его к памяти (`GameService.resolveRound`, `RoundCancellations.cancel`); сбой до этого (событие не записалось, соединения с БД нет) память не трогал — пересборки нет и движок остаётся готовым. Журнал: первый сбой окна — со стеком, дальше строка не чаще раза в минуту (`util/FailureLog.java`; расчёт пишет `RoundSchedulerService`, пересборку — `EngineRebuildService.recoverAfterFailure(cause, key, nowMs)`). Часы, ушедшие назад за момент сбоя, считаются «давно» (как в `util/LogThrottle`): окно не ждёт, пока часы догонят. Тесты со своими часами делят один планировщик: `RoundSchedulerService.forgetFailedAttempts()` вызывается в `LiveGameTestBase` перед каждым тестом и в `CleanDatabasePerTestClass` перед каждым классом (без этого сбой одного теста откладывал окно BTC в другом, порядок методов решал, пройдёт ли `MultiMarketGameFlowTest`). Не закрыто: если не удаётся каждая из серий, каждая пересобирает движок раз за шаг отсрочки. Измерения до исправления — ревью ядра 2026-10-02, находка 3: пересборка стоит 25 мс + 5,6 мкс на событие журнала, 510 мс при 91 тыс. событий. Тест `SettlementBackoffSchedulerTest`.
14. **Границы раундов (Р-40) держит ядро, а не память конвейера цен.** Раунд рынка M с окном `[S, E)` при расчёте открывается по цене закрытия строки `round_results` рынка M со статусом `SETTLED`, окно которой кончается в `S` — любой серии; открытие конвейера игнорируется, первая свеча пути открывается там (low/high расширены). Та же цена открытия — в каждом DTO идущего раунда (`rounds`, `round`, `myPositions`), в том числе когда конвейер открытия не знает совсем (тогда график рисуется по плоской линии от него). Отменённый предыдущий раунд закрытия не имеет — подмены нет. Если две строки разных серий кончаются в одной границе с разными закрытиями (данные до этого правила) — считается строка более длинной серии, которую планировщик рассчитывает первой. Закрытие раунда не меняется никогда. Только `mode=live`: ряд `replay` записан, его следующее окно открывается по открытию следующей свечи, а не по закрытию предыдущей. Цены берутся из памяти (`service/BoundaryPrices.java`): читаются из БД при сборке состояния рядом с пересборкой (по одному запросу на серию, по индексу `(market, interval, window_start_ms)`), добавляются после фиксации расчёта, чистятся позади указателей; обращений к БД под блокировкой движка нет. Тест `BoundaryContinuityTest`, `BoundaryPricesTest`.
15. **Закрытие рынка возвращает ставки во всех окнах.** `RoundCancellations.closeSeries` отменяет с возвратом идущее окно и окно ставок (даже пустые) и **каждое** другое окно серии со ставкой без итога — по индексу окон со ставками в `EngineHub` (`domain/BetWindows.java`; его ведёт `EventApplier`, в реплее тоже, подмена состояния подменяет и его). Так же, из того же индекса, пересборка возвращает ставки рынку, закрытому в БД (п.8), по обеим сериям. В игре, идущей вперёд, ставки лежат только в двух окнах у указателя; ставка не должна от этого зависеть. Тест `CloseRefundsEveryWindowWithABetTest`, `SeedingKeepsPendingBetsTest`; ревью ядра, находки 7 и 8.

## 6. События и БД

- `GameEvent.BetPlaced`, `BetCancelled`, `RoundResolved`, `RoundCancelled` получают необязательное поле `market`; `null` при чтении означает `BTC`. `EventStore.CURRENT_SCHEMA_VERSION` остаётся 1. Старые золотые фикстуры событий должны читаться как есть; фикстуры с рынком — в отдельном каталоге.
- Миграция `V7__markets.sql`: таблицы `markets` (поля записи `Market`; строка BTC) и `price_snapshots`; `round_results`, `player_round_history`, `oracle_records` получают `market TEXT NOT NULL DEFAULT 'BTC'`; `oracle_records` — `asset_index INT NOT NULL DEFAULT 0`; индексы `(market, interval, window_start_ms)`.
- `round_results.open_price_cents/close_price_cents` и `oracle_records.price_cents` — цена лота в сотых, то есть `raw × 10^priceDecimals`.
- Канонический JSON итогов: для BTC без изменений; для остальных рынков добавляется корневой ключ `market`. Сохранённый `canonical_json` не пересчитывается никогда.

## 7. Оракул v2 (FIXED INTERFACE O)

1. **Запись** сервер → chainsvc: `{seq, ts, priceCents, resultsHash, source, sourceTs, asset}`; `asset` — индекс реестра, по умолчанию 0. В Rust поле `#[serde(default)]` (файл очереди со старыми записями читается).
2. **Announcement**: `(seq ts priceCents resultsHash sourceFlag sourceTs)` при `asset == 0` и `(seq ts priceCents resultsHash sourceFlag sourceTs asset)` при `asset > 0`. Декодер lineage читает оба (`asset` по умолчанию 0).
3. **Статус** `GET /v1/oracle/status` дополняется `maxKnownSeq` (максимум по accepted, confirmed, conflicts, pending, in_flight) и `recordFormat: 2`.
4. **Пол seq.** Сервер перед выдачей первого `seq` и при каждом старте поднимает свой счётчик до `maxKnownSeq` (`ServerMetaRepository.raiseOracleSeqTo`, монотонно). При `herd.oracle.require-seq-floor=true` (стенд, VPS) планировщик не рассчитывает раунды, пока пол не получен хотя бы раз. Сервер не шлёт записи с `asset > 0`, пока статус не показал `recordFormat ≥ 2`.
5. **Реестр**: `GET /api/markets/registry.json` — `[{index, id, kind, symbol, priceDecimals, source, sourceRef, listedAtMs}]`.
6. **Журнал записей для верификатора**: `GET /api/oracle/records?fromSeq=&limit=` — `{firstSeq, records:[{seq, roundId, marketId, asset, ts, priceCents, resultsHash, state}]}`; `limit ≤ 1000`.
7. **Верификатор** (`tools/verify-oracle`): читает announcement из 6 и 7 элементов (3-элементный первый остаётся в «неразобранных»); со `--stand-url` берёт соответствие `seq → раунд` из журнала записей, сверяет `sha256(results.json)`, цену закрытия и индекс актива; `seq` меньше `firstSeq` стенда показываются как «до эпохи этой БД» и проверяются только по цепи; `--from-seq`; сетевые ошибки — код выхода 2; `--strict` — пропуски и несопоставленные `seq` дают код 1. Офлайн-тесты на фиксированных данных.
8. `MAX_RECORDS_PER_SPEND` поднимается до 40 при наличии теста на симуляторе с 40 записями.

Источник правды — `web/src/api/contract.ts` (раздел «Markets and categories» и изменённые типы). Сервер зеркалит типы в `server/.../dto`. Транспорт прежний: `POST /api/rpc/<method>` с `{"args":[…]}`.

Все цены в ответах — сырые, строкой с `priceDecimals` знаками рынка. Ограничены по частоте `authChallenge`, `authVerify`, `placeBet`, `cancelBet`. `home` остаётся и описывает BTC.

Клиентский расчёт ликвидации повторяет серверный так: цена умножается на `10^(priceDecimals − 2)`, размер округляется до 8 знаков, применяются прежние формулы с 2 знаками и `l = 1/(2·maxLeverage)`, результат делится обратно.

## 11. Что не проверено

- Условия использования данных Polymarket (`polymarket.com/tos`) не читались — **UNVERIFIED**; по принципу проекта условия источников проверяет тот, кто разворачивает (`docs/selection/final_top3.md` §«Принцип»).

- Частота «плоских» раундов на шансах (цена не изменилась за 3 минуты) — не измерялась.
- Рост журнала событий: около 450 расчётов раундов и 1 400 ставок ботов в час при 18 парах; снимки состояния для быстрого старта не делаются.
