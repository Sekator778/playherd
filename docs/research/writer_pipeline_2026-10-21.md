# Конвейер писателя: логика не ждёт диск

Дата: 2026-10-21. Основание — D-95, D-96, D-107; вопрос Алекса 2026-10-21 «как мы реализуем LMAX, где скорость — это память». Метод — `docs/kb/topics/methods.md`, «Конвейер писателя». Код — `server/.../core/` (`CoreWriter`, `JournalStage`, `OutputStage`, `WriterBatch`, `WriterSlot`), `ReadViews.prepareBatch/publish`.

## 1. Что было

Один поток делал за пачку: применение команд в памяти (≈ 4 мкс на ставку), запись в журнал с синхронизацией (на Linux ≈ 2,2 мс, `journal_chronicle_2026-10-21.md` §6), публикацию представлений F8, действия после коммита, ответы. Поток логики ждал диск на каждой пачке.

## 2. Что стало

| Этап | Поток | Что делает |
|---|---|---|
| Логика | `herd-core-writer` | берёт команды, применяет их в памяти под блокировкой движка, **строит представления F8** состояния после пачки (не публикуя), передаёт пачку и берёт следующую; ждёт только места в конвейере (обратное давление, `herd.writer.pipeline-depth`, по умолчанию 8 пачек) |
| Журнал | `herd-core-journal` | берёт всё, что ждёт, пишет **одной записью** журнала с **одной синхронизацией** (групповой коммит); единственное место записи в журнал |
| Выход | `herd-core-output` | для синхронизированной пачки публикует представления (`ReadViews.publish`), запускает действия после коммита (push), отвечает вызывающим |

Передача между этапами — `LinkedBlockingQueue`; место в конвейере — `Semaphore` (одно разрешение на пачку; «дождаться опустошения» = взять все разрешения). Disruptor не подключён (решение и цифры — kb). Журнал событий, не команд: байты записи и полезной нагрузки те же; в одной записи теперь могут быть события нескольких пачек (читатель, пересборка и проектор от границ записей не зависят; версия представлений каждой пачки — её собственный последний `seq`).

## 3. Правила и где они держатся

| Правило | Как |
|---|---|
| Ответ только после синхронизации | ответ — в `OutputStage`, пачка приходит туда из `JournalStage` после возврата `appendAll`; тест `withTheSyncBlockedTheLogicThreadGoesOnButNothingIsAnsweredPublishedOrPushed` |
| Представление не показывает несинхронизированную версию | `ReadViews.prepareBatch` строит следующий снимок поверх последнего подготовленного (`tail`), `current` меняет только `publish`; окна закрытых раундов (`ClosedRounds`, общая изменяемая структура) отмечаются при публикации; снимок старой линии (после полной публикации) отбрасывается (`epoch`); тесты `CoreWriterPipelineTest`, `ReadViewsTest` |
| Push только после синхронизации | действия после коммита идут в `OutputStage` |
| Порядок журнала = порядок применения | одна очередь, один журнальный поток, события склеиваются в порядке пачек; тест на 64 клиентах, 40 команд каждый |
| Сбой записи/синхронизации | журнальный поток ставит `failure`, отбрасывает всё, что пришло за сбойной группой (`poisoned`, не пишет), будит логику; логика останавливается, ждёт возврата всех переданных пачек, вызывает `onRollback`, пересобирает движок из журнала (`Host.recover`) и отвечает 503 всем непосинхронизированным (причина приложена); пачка, применённая после замеченного сбоя, отбрасывается так же; тесты `aFailedSyncWithSeveralBatchesInFlight…`, `aFailedSyncWhileTheLogicThreadIsIdle…` |
| Снимки F5, пересборка, строки леджера, `releaseReservation` — только при состоянии «в памяти = в журнале» | `GameService.enterGate()` → `CoreWriter.enterGate()`: берёт замок gate (логика не начинает пачку) и ждёт опустошения конвейера; если за это время синхронизация упала — отпускает gate и ждёт пересборки; gate справедливый; тесты `whoEntersTheGate…` |
| Команда, применившая часть и упавшая | пачка до неё передаётся, логика ждёт опустошения, пересобирает, отвечает сама; представления для такой пачки не строятся |
| Поток писателя умер (исключение вышло из потока: `Error` там, где его никто не ждёт) — 2026-10-22 | каждый из трёх потоков запущен через `CoreWriter.guarded`: вышедшее исключение → `died`: писатель сразу перестаёт принимать команды (`running = false`), отдельный поток `herd-core-stop` закрывает его — все ждущие (в очереди, взятые логикой в пачку, перенесённые, в конвейере) получают 503 — и вызывает `Host.stageDied`; сервер делает `Quarkus.asyncExit(1)`, контейнер перезапускается (`restart: unless-stopped`) и пересобирается из снимка и журнала. До этого `enterGate` отказывает 503 (движок может держать пачки, которых в журнале нет и не будет: снимок унёс бы их в следующий запуск), опустошение конвейера (`drain`) больше не ждёт вечно. Если умер поток вывода, пачка уже в журнале, а вызывающий получил 503: повтор ставки с тем же `clientRequestId` после перезапуска возвращает первый ответ (событие ставки несёт `clientRequestId`, `EventApplier` запоминает его при пересборке). Тесты `aJournalThreadThatDies…`, `aJournalThreadThatDiesWithBatchesQueued…`, `anOutputThreadThatDies…`, `aLogicThreadThatDiesWithCommandsInHand…` (сбой вызывается `crashForTests`) |
| Логика не трогает диск, БД, сеть | `EngineIoRuleTest` (обход графа вызовов: `CoreWriter`, `OutputStage`, `WriterSlot`, `WriterBatch` не достигают приёмников вовсе, `JournalStage.write` — только `EventStore.appendAll`; запись в журнал вызывают лишь перечисленные классы), `IoGuard` (вид `disk` в `EventStore`: поток логики не читает и не пишет журнал вне `EngineRebuildService.rebuildStateLocked`) |

Linux, 1024 — синхронизация 97 %, 1,6 пачки на синхронизацию, логика 78 %.

## 5. Открытое

- Выходной этап — узкое место на Mac при 1024 клиентах (будить вызывающих потоков 15 мкс на команду); не распараллелен, не оптимизирован.
- Диск VPS и the bench box не измерялся; Linux-числа — виртуальный диск OrbStack.
- Отключение питания и падение ядра не проверялись (как в `journal_chronicle_2026-10-21.md` §7).
- Между применением и синхронизацией движок впереди журнала. Читатели памяти движка вне представлений F8 найдены 2026-10-22 (поиск по `server/src/main/java`: `hub.`, `.ledger()`, `.betBook()`, `engineLock`, `RoundProgress`, `findNext`, `@Scheduled`). Показывал несинхронизированное одно место — push-тикер (`PushTicker.windows`) брал живой курсор раунда из `RoundProgress`, который расчёт двигает на потоке логики до синхронизации: уведомление могло уйти раньше, чем представления покажут сдвиг, и второго не было бы [вывод из кода]. Исправлено: курсоры берутся из опубликованного снимка (`ReadViews.Snapshot.cursor`). Остальные читают живой курсор только для решения, которое команда на потоке логики проверяет заново (`RoundSchedulerService.resolveOverdueRounds`, `GameService.openRounds`, `ServerBotPorts.markets`, `BotService.planBettingWindows`), или счётчик для статуса администратора (`ledgerRowsStatus`, предпроверка `flushLedgerRows`, дальше — через gate). `withdrawalAwaitingChain` вызывается только внутри команд `confirmWithdrawalOnChain`/`failWithdrawalOnChain` (поток логики); строка журнала выключателя (`noteBreaker`) берёт цифры из опубликованного снимка (`snapshot().economy()`) — оба безопасны.
- Смерть потока писателя теперь останавливает сервер (§3); перезапуск после неё на стенде не проверялся (в тестах — только остановка и ответы).
